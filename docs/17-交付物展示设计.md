# 交付物展示设计

需求阶段归档范围（2026-09-22）：聊天 `present_files` 可展示关联仓库文件，但阶段收集仅归档当前工作空间或会话输出目录内的合格文件。历史展示或工件记录中的目录外文件、解析后越界的目录链接与隐藏路径项不参与归档，也不阻断其他合法产物。目录内文件仍执行非空、大小及版本校验；没有合格产物时不能提交阶段。详见 [目录范围修复设计](designs/2026-09-22-requirement-delivery-scope-design.md)。

## 1. 背景

项目已实现 `present_files` 交付工具、交付数据传递、聊天区交付物列表和右侧预览面板，但最终用户感知仍是“列出了几个文件”，没有完整达到 WorkBuddy 的交付体验：

- 不同类型的交付物在聊天区缺少明确的视觉语义。
- 图片、文档、表格、演示文稿、代码、视频和网页的展示形式没有统一规范。
- 卡片点击、首项自动打开、内置预览和系统打开之间的路由边界不够清晰。
- 实时工具事件依赖全局 `presentedFiles`，一个会话多次交付时，旧消息存在误用最新交付批次的风险。

本设计参考 `/Users/xiaozhongyuan/Downloads/README.md` 的 WorkBuddy-style `present_files` 思路，在现有三栏布局和右侧预览能力上完成前端收口。

## 2. 设计目标

1. `present_files` 仍是任务产生可查看成果时的唯一交付入口。
2. 聊天区中每个交付物都显示为可点击的类型化卡片，而不是纯文本路径或同质化文件列表。
3. 交付顺序表达优先级，工具成功后自动打开第一项。
4. 点击卡片时统一在右侧内置预览区打开。仅当文件无内置预览器时，才提供“用默认应用打开”的降级操作。
5. 实时会话、会话重载和多次交付的展示结果一致。
6. 复用现有 `PreviewPanel` 和各类预览器，不引入第二套文件预览架构。

## 3. 非目标

- 不改变 Agent 生成文件的方式。
- 不重做文档、表格、PPT 和 PDF 的底层渲染引擎。
- 不把完整文件内容直接嵌入聊天消息流。
- 不将仅被读取的文件或局部修改的源码自动视为交付物。
- 不在本次设计中新增交付物编辑或版本回滚能力。

## 4. 当前实现对照

### 4.1 已有能力

| 链路 | 当前实现 |
|---|---|
| 工具定义 | `src/agent/tools/present_files.ts` 验证文件/URL，返回 `path/url/title/type/icon/size/exists` |
| Agent 约束 | `src/agent/engine.ts` 要求有可查看结果时以 `present_files` 结束 |
| 实时状态 | `frontend/src/store/useStore.ts` 在工具结束时保存列表并打开首项 |
| 消息卡片 | `frontend/src/components/ChatArea.tsx` 已有 `PresentFilesCards` |
| 右侧预览 | `ArtifactPanel.tsx` + `PreviewPanel.tsx` 已支持文档、PDF、文本、网页、表格、PPT 和图片 |
| 系统操作 | `frontend/src/utils/openFile.ts` 已支持系统打开和在文件夹中定位 |
| 历史恢复 | `application.electron.ts` 和 `src/agent/provider.ts` 保留 `present_files` 完整 `details` |

### 4.2 主要差距

1. 卡片只直接消费工具返回字段，没有独立的前端文件类型规则。
2. 所有文件共用几乎相同的紧凑卡片，图片没有缩略图，各文档类别的颜色和标签语义不足。
3. 文件类型判断分散在 `present_files.ts`、`ChatArea.tsx` 和 `PreviewPanel.tsx`，支持范围可能不一致。
4. `parsePresentedFiles()` 在实时消息不含 `details` 时回退到全局 `presentedFiles`，无法稳定表达“每条工具消息自己的交付批次”。
5. `ArtifactPanel` 只优先使用最新的全局列表，“当前批次”和“会话历史交付物”的语义没有明确区分。
6. 视频、代码和部分数据文件尚未有对应的内置预览策略。

## 5. 总体方案

采用“统一卡片骨架 + 文件类型适配器”。

```text
present_files 工具结果
        │
        ▼
交付批次 DeliveryBatch
        │ 每条工具消息独立保存
        ▼
normalizePresentedFile()
        │ 统一分类、标签、图标、颜色、预览能力
        ▼
ArtifactCard
        │ 点击
        ▼
openPreview(PreviewTarget)
        │
        ├─内置预览器
        └─UnsupportedPreview → 系统默认应用
```

不让卡片组件自行判断扩展名，也不让预览面板重复维护一份类型表。一个纯函数适配器输出稳定的前端展示模型，聊天卡片和右侧预览共享它。

## 6. 数据模型

### 6.1 工具输出

保留现有 `PresentedFile` 协议，其字段来自主进程的安全验证：

```ts
interface PresentedFile {
  path?: string;
  url?: string;
  title?: string;
  type?: string;
  icon?: string;
  size?: string;
  exists?: boolean;
}
```

### 6.2 前端展示模型

新增由前端适配器产生的 `ArtifactViewModel`：

```ts
type ArtifactKind =
  | "web"
  | "image"
  | "document"
  | "spreadsheet"
  | "presentation"
  | "video"
  | "code"
  | "data"
  | "text"
  | "unknown";

interface ArtifactViewModel {
  key: string;
  source: PresentedFile;
  kind: ArtifactKind;
  displayName: string;
  typeLabel: string;
  extension: string;
  sizeLabel?: string;
  icon: string;
  tone: string;
  previewMode: "internal" | "external-fallback";
  previewTarget: PreviewTarget;
  thumbnailUrl?: string;
}
```

`type` 和 `icon` 保留为工具返回的元数据，但前端不盲目信任它们。适配器根据 `url/path/type` 得到最终展示类型，保证历史数据和新数据都能正常呈现。

### 6.3 交付批次归属

每条成功的 `present_files` 工具消息必须拥有自己的 `presentedFiles` 数组。

- 实时路径：`tool_execution_end` 直接把 `details.files` 写入对应 `Message`。
- 重载路径：从持久化消息 `content.details.files` 解析。
- 全局 `presentedFiles` 只表示“右侧面板当前批次”，不再作为历史聊天卡片的数据回退。

这样可以保证同一会话中先交付报告、后交付图表时，两组卡片各自稳定。

## 7. 文件类型和展示规则

| 类型 | 格式 | 聊天卡片 | 点击后 |
|---|---|---|---|
| 网页 | URL, html, htm | 网页图标、域名/文件名、“网页”标签 | 右侧网页预览 |
| 图片 | png, jpg, jpeg, gif, svg, webp | 安全缩略图 + 文件名和尺寸 | 右侧图片预览 |
| 文档 | pdf, docx | 文档色标识、格式标签、大小 | 右侧 PDF/Word 预览 |
| 表格 | xlsx, xls, csv, tsv | 绿色表格标识、格式标签、大小 | 右侧表格预览 |
| 演示文稿 | pptx, ppt | 橙色演示标识、格式标签、大小 | 右侧 PPT 预览 |
| 代码 | py, js, ts, tsx, jsx, go, rs, java, c, cpp, css, sh | 代码标识、语言标签、大小 | 右侧文本/代码预览 |
| 数据 | json, yaml, yml, xml | 数据标识、格式标签、大小 | 右侧文本预览 |
| 文本 | md, txt | 文本标识、格式标签、大小 | 右侧 Markdown/文本预览 |
| 视频 | mp4, mov, webm | 播放标识、格式标签、大小 | 右侧视频预览 |
| 其他 | 未识别格式 | 通用附件标识、扩展名、大小 | 不支持提示 + 系统打开 |

类型映射不使用 emoji 作为唯一识别信息。卡片同时使用图标、颜色和文字标签，保证可访问性和跨平台一致性。

## 8. 卡片设计

### 8.1 统一骨架

每张卡片包含：

1. 类型视觉区：类型图标，图片类则为缩略图。
2. 主信息：展示名称，单行省略，悬停可看完整名称。
3. 次信息：文件类型标签 + 文件大小；URL 显示域名。
4. 主操作：整张卡片点击后预览。
5. 次操作：本地文件提供“在文件夹中显示”，与主点击区分离。

卡片容器使用自适应网格，在中栏较宽时多列展示，窄屏时自然回落为单列。

### 8.2 图片缩略图

图片卡片可以使用现有安全文件读取/preview 能力生成缩略图源。缩略图只作为卡片装饰，加载失败时回退到图片类型图标，不影响卡片点击。

### 8.3 交付批次标题

每次 `present_files` 输出在聊天中显示为一个批次：

- 标题：“交付物”。
- 计数：“N 项”，URL 也计为一项，不固定写“N 个文件”。
- 说明：有 `explanation` 时显示简短交付说明，不在卡片中重复长文内容。
- 部分失败：有 `problems` 时显示非阻塞警告，成功项仍正常可用。

## 9. 交互和预览路由

### 9.1 交付成功

1. `present_files` 成功返回。
2. Store 把文件数组绑定到当前工具消息。
3. 聊天区渲染该批次的类型化卡片。
4. Store 把该数组设为右侧面板的当前批次。
5. 自动打开第一项，显示右侧预览面板。

自动打开只发生在实时工具成功时。用户重新进入历史会话时，聊天卡片会恢复，但不强制弹开右侧面板。

### 9.2 点击卡片

1. 卡片把完整 `PreviewTarget` 传给 `openPreview()`。
2. Store 打开右侧面板并切换到 `preview` 模式。
3. `PreviewPanel` 根据统一类型适配结果选择渲染器。
4. URL/HTML 使用网页预览；支持的本地文件使用对应内置预览器。
5. 未支持格式进入 `UnsupportedPreview`，展示文件信息和“用默认应用打开”。

### 9.3 键盘与可访问性

- 卡片使用真实 `<button>` 或等价语义，支持 Tab、Enter 和 Space。
- 图标不是唯一类型线索，必须同时存在文字标签。
- 文件名被截断时保留 `title` 提示。
- 焦点态清晰可见，不只依赖 hover。
- 缩略图使用空 `alt`，文件名由卡片文本提供。

## 10. 异常与降级

| 场景 | 处理 |
|---|---|
| `files` 为空 | 工具返回错误，不生成空交付批次 |
| 部分文件不存在 | 渲染有效项，批次显示 `problems` 警告 |
| 所有项无效 | 工具消息以错误样式展示，不打开预览区 |
| localhost 不可达 | 保留现有工具端探测，不创建可点击的无效卡片 |
| 缩略图加载失败 | 回退为类型图标，卡片仍可点击 |
| 内置预览失败 | 显示错误摘要和系统打开操作 |
| 未识别扩展名 | 使用通用附件卡和 `UnsupportedPreview` |
| URL 无路径名 | 展示域名，不显示空标题 |
| 历史旧消息缺少新字段 | 适配器从 `path/url` 推导，不做数据库 migration |

## 11. 组件边界

### `artifactPresentation.ts`

- 输入：`PresentedFile`。
- 输出：`ArtifactViewModel`。
- 责任：扩展名解析、文件分类、类型标签、颜色和预览模式映射。
- 不依赖 React，可单元测试。

### `ArtifactCard.tsx`

- 输入：一个 `ArtifactViewModel` 和点击回调。
- 责任：渲染通用骨架和类型化视觉，处理预览、文件夹定位和键盘交互。
- 不解析工具输出，不直接读取全局 store。

### `PresentFilesBatch.tsx`

- 输入：一条 `present_files` 消息对应的交付数组、说明和问题列表。
- 责任：批次标题、计数、警告和卡片网格。
- 不从全局最新交付列表猜测当前消息的数据。

### `PreviewPanel.tsx`

- 保留右侧预览容器职责。
- 改为消费统一类型映射，避免独立维护不一致的扩展名 `switch`。
- 预览器只关心如何渲染目标，不关心交付物来自哪条消息。

## 12. 验收标准

### 12.1 功能验收

1. Agent 一次交付 HTML、PNG、PDF、DOCX、XLSX、PPTX、MP4、TS、JSON 和未知格式时，聊天区按原始顺序显示卡片。
2. 每类卡片都有可识别的图标/缩略图、类型标签、名称和可用时的文件大小。
3. 工具结束后只自动打开第一项，其余项保持为可点击卡片。
4. 点击任意卡片均打开右侧预览区并选中对应项。
5. 无内置预览器的文件显示明确降级提示，可用系统默认应用打开。
6. 同一会话连续两次调用 `present_files` 后，第一批卡片不会变成第二批文件。
7. 重载会话后所有历史批次仍正确展示，不自动强制弹开预览区。
8. 部分文件失败时，成功卡片可用，警告信息可见。

### 12.2 响应式与可访问性验收

1. 聊天区宽度不足时卡片回落到单列，不溢出消息区。
2. 长文件名不挤压操作按钮，可通过悬停查看完整名称。
3. 仅使用键盘可以聚焦、打开卡片和使用次操作。
4. 深色和浅色主题下的类型色、焦点态和文字对比度可读。

## 13. 测试策略

### 单元测试

- 类型适配器：扩展名、大小写、带 query 的 URL、无扩展名 URL、未知格式。
- 展示名称：`title` 优先，其次文件名，最后域名。
- 交付解析：实时消息和持久化消息生成相同批次。
- 预览路由：每个 `ArtifactKind` 进入正确预览器或降级页。

### 组件测试

- 交付批次渲染顺序和计数正确。
- 卡片点击调用 `openPreview()` 且传入完整目标。
- 文件夹按钮不触发卡片的预览点击。
- 图片缩略图失败时显示回退图标。
- 多批次消息各自显示自己的文件。

### 端到端验证

- 运行真实 `present_files`，验证首项自动打开。
- 逐一点击 HTML/URL、图片、PDF、DOCX、XLSX、PPTX、代码和未知文件，验证右侧路由。
- 在同一会话执行两次交付并重载应用，验证历史稳定性。
- 验证窄屏、深色主题、键盘操作和长文件名。

## 15. 实施顺序建议

1. 先建立统一类型适配器和单元测试。
2. 再把 `present_files` 数据绑定到消息，修复多批次和重载一致性。
3. 实现类型化卡片和批次组件，先打通文档、表格、PPT、图片和 URL 的最小端到端链路。
4. 统一 `PreviewPanel` 路由，再补齐代码、数据、视频和未支持文件的降级。
5. 最后增加图片缩略图、响应式和可访问性细节，并执行端到端验收。

该顺序保证每一阶段都有可运行的端到端结果，不会为了完成所有类型细节而拆掉已经可用的交付链路。
