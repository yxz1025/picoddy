# 研发阶段：需求澄清与多仓库设计流程

日期：2026-09-10  
版本：0.2  
状态：执行方向已确认，详细流程待评审；非已实现功能说明

## 1. 目标与已确认原则

本方案细化[产品—研发—测试全流程总览](./产品研发测试全流程与产物总览.md)中的研发设计环节。

由软件架构师统一接收产品交付包，关联用户端前端、管理后台前端、后端等相关仓库，依据真实代码与各仓库设计要求完成增量设计，将研发文档分别保存到对应仓库。

核心原则：**拿到需求先审查和澄清，不是一股脑生成文档。** 不清晰、不合理、互相冲突或缺少关键规则的需求，应向产品提出有依据的问题，由产品补充或确认；不能把 AI 假设包装成产品决定。

本文规定设计、任务人工评估和授权开发的流程边界。专家源包的配置能力与客户端是否加载、真实场景是否验证是不同事项，不能仅凭文档或源包更新声称完整流程已上线。

## 2. 责任边界

| 角色 | 职责 | 不得代替的决定 |
| --- | --- | --- |
| 软件架构师 | 需求审查、代码核查、问题分析、方案建议、跨仓库协调、设计和自检 | 不擅自改变产品范围、业务规则或批准自己的方案 |
| 产品经理/业务方 | 解释需求、补充规则、确认范围、原型和验收条件 | 不用模糊业务描述替代明确接口与实现约束 |
| 仓库研发负责人 | 确认技术现状、仓库边界、项目规范和方案可行性 | 不以当前实现为理由默默删改需求 |
| 测试人员 | 提前检查可测试性、场景与风险覆盖 | 不将设计检查等同于系统测试通过 |

业务问题交给产品，技术事实和仓库规范问题交给研发；涉及双方取舍时共同确认，避免把全部问题都抛给产品。

## 3. 输入与仓库登记

### 3.1 产品交付输入

- 正式需求单编号，以及该需求内的功能条目/验收编号。
- PRD 文件及固定版本。
- 对应原型文件或固定版本链接。
- 产品评审结论、已知待确认项与限制。

PRD 尚未评审也可以进入需求分析，但状态必须明确，不能直接当作已确认研发基线。若没有正式编号，可以先在会话中澄清；正式归档前需确认稳定编号，不自行制造与业务系统冲突的编号。

### 3.2 仓库登记

| 字段 | 说明 |
| --- | --- |
| `repo_id` | 稳定仓库标识，如 `admin-web`，不使用个人本地目录作为身份 |
| 仓库地址、本地目录 | 区分远程来源与本机可读取工作位置 |
| 系统职责 | 用户端、管理后台、业务服务等，可包含多个模块 |
| 关联类型 | 修改、依赖或参考 |
| 基准分支和提交 | 记录本次代码分析依据，分支名不能代替提交版本 |
| 本地变更状态 | 是否存在未提交改动、哪些与本需求有关 |
| 规范入口 | 由仓库实际约定决定；可位于 `docs/development/`、`docs/architecture/` 等目录，并在规范中登记 |
| 负责人 | 技术事实和方案确认的责任人 |

AI 可以建议关联仓库，最终范围由研发确认。仅有远程地址不代表代码已经读取；克隆、切分支、更新代码或写入文件需在授权范围内进行。不得为便于分析覆盖用户本地改动。

牵头仓库由研发明确指定，用于保存跨仓库问题和协调记录，不默认认为后端就是牵头仓库。未指定时可在会话中先列问题，不随意写到某个仓库。

## 4. 仓库前置准备与老项目初始化

每个仓库应提供统一规范入口，已有文档优先引用。入口不固定为 `docs/development/`；如果仓库已有 `docs/architecture/`、`docs/designs/`、`docs/plans/` 等分类，应先识别其实际含义并建立映射：

```text
docs/development/ 或已有 docs 分类/
├── design-guidelines.md
├── project-context.md
└── architecture.md
```

| 文件 | 应说明的内容 |
| --- | --- |
| `design-guidelines.md` | 必读资料、分层和编码约束、接口/组件约定、设计深度、产物模板、验证要求、文档归档规则 |
| `project-context.md` | 项目职责、技术栈、目录、运行构建方式、测试入口及依赖系统 |
| `architecture.md` | 主要模块、调用和数据流、权限边界、外部依赖、重要设计决策 |

规范可引用 README、接口定义、组件文档等权威来源，不复制维护相同内容。跨仓库需求编号、身份和引用一致性是共同要求；与仓库既有归档规则冲突时由负责人确认映射后再写入。

老项目没有这些资料时，先做最小初始化：

1. 读取现有项目说明、配置和代码结构。
2. 深入本次需求相关入口、调用链和测试，不要求读完所有历史代码。
3. 整理事实、证据及未核实项，形成基线草案。
4. 由研发核对关键约束后使用；不阻塞于无关模块的文档补齐。

项目基线描述现状，不带某个需求编号；需求级规格描述本次目标变化。不得给全部历史功能批量生成 `spec`，也不得在初始化时自动重构、增加依赖或修改业务代码。

## 5. 主流程与推进条件

```text
接收产品交付包、登记仓库
    ↓
产品资料完整性审查
    ↓
读取仓库规范和相关代码，核实可行性与现状
    ↓
形成问题清单：业务问题 → 产品；技术问题 → 研发
    ↓
补充资料、确认决定、更新 PRD/原型/验收条件
    ↓
复核问题闭环，确认设计输入基线
    ↓
跨仓库分工与共享契约设计
    ↓
各仓库详细设计与任务拆解，分别归档
    ↓
交叉检查、研发评审、任务人工评估与调整
    ↓
人工确认任务基线，交付“可开发设计包”
    ↓
明确授权执行指定任务后，才进入代码实现与验证
```

需求审查和代码分析可以迭代进行：先发现缺口，再用代码证据补充问题；不要求需求完全澄清后才允许读取代码。

### 5.1 第一步：先审查，不先生成完整设计

审查以下内容：

| 维度 | 典型检查 |
| --- | --- |
| 目标与范围 | 要解决什么问题？哪些角色、系统和场景在本次范围内？ |
| 业务规则 | 状态转换、前置条件、计算口径、有效期、重复操作如何处理？ |
| 数据与权限 | 数据来源、字段含义、可见范围及操作权限是否清晰？ |
| 交互一致性 | PRD 与原型是否矛盾？失败、取消、空态是否定义？ |
| 验收条件 | 是否能观察和验证？“快速”“实时”“支持全部”是否缺少边界？ |
| 现有实现 | 哪些能力已存在？实际行为与文档是否冲突？ |
| 可行性与风险 | 是否依赖不可用接口、存在安全风险或与目标项目约束冲突？ |

不为所有需求强加性能指标或复杂异常模板；只提出会影响该需求设计和验证的实质问题。

这一阶段允许输出问题清单、代码证据和有限的方案选项，不批量生成看似确定的 `spec/design/tasks`。完整性不足不等于所有需求都无法推进，应说明受影响范围。

### 5.2 第二步：提出可回答的问题

每个问题要说明“哪里不明确、依据是什么、为什么影响设计、需要谁决定”，而不是泛泛要求产品“把 PRD 补完整”。

| 字段 | 要求 |
| --- | --- |
| 问题 ID | `<需求编号>-Q001`，稳定且可引用 |
| 对应需求/验收 | 引用具体条目，不只引用整份 PRD |
| 来源与证据 | PRD 章节、原型页面、仓库文件/符号和基准提交 |
| 问题描述 | 区分缺失、歧义、冲突、可行性风险 |
| 影响范围 | 受影响仓库、模块、方案和验收 |
| 阻塞性 | 阻塞整体、阻塞部分或非阻塞，并说明理由 |
| 建议与选项 | 提供必要的选择及取舍，不将建议写成已决定 |
| 确认角色 | 产品、业务、研发或共同确认 |
| 回复与状态 | 保留实际回复、决定、文档回写及复核结果 |

示例：原型有“批量审核”，PRD 未说明部分失败处理，而现有接口只支持逐条审核。应询问“允许部分成功还是必须全部成功”，说明它影响接口、事务边界、页面反馈和验收，不能自行选择循环调用就认为满足需求。

对“不合理”的判断应有依据，例如互斥要求、明确安全风险、已核实的技术限制或与业务目标不匹配；不能只因偏好不同否定需求。重大取舍提供替代建议，由有权人员决定。

### 5.3 第三步：产品补充与问题闭环

问题处理过程建议记录为：提出 → 待确认 → 已答复待回写 → 已回写待复核 → 已关闭。拒绝或延期处理的问题保留原因和剩余风险。

- 产品补充业务规则，并同步受影响的原型与验收条件。
- 架构师可提出修改建议；修改权威产品文件需获得相应授权，不能只在研发文档里悄悄改业务定义。
- 聊天答复不自动等于文档闭环：记录答复来源，回写或形成受控补充记录，并明确优先关系及确认版本。
- 技术事实由研发确认，重要结论保留代码证据。
- 复核冲突是否消除、依赖方是否理解一致，再关闭问题。

### 5.4 第四步：设计准入

完整设计开始前确认：

- 产品范围、关键业务规则和适用验收条件已明确。
- PRD、原型和补充决定之间没有未解决的阻塞冲突。
- 关联仓库、规范和关键代码已可读取，分析基准可定位。
- 跨仓库职责及关键依赖已确认到可设计程度。
- 产品与研发确认本轮输入基线及未决项处理方式。

非阻塞问题可以保留，但需说明为何不影响当前设计。部分阻塞时，可在明确范围后设计独立且已确认的部分，文档标记“部分设计草案”；不得把整体标为可开发。核心规则仍缺失时停在澄清阶段，不用大量假设填满正式方案。

## 6. 基于代码的增量设计

### 6.1 代码证据与需求映射

在修改仓库中核查入口、调用链、业务服务、数据访问、接口/组件、权限、异常处理和测试，形成映射：

| 需求条目 | 仓库/模块 | 当前实现证据 | 目标行为与差距 | 处理方式 |
| --- | --- | --- | --- | --- |
| `<需求编号>-F001` | 用户端前端 | 文件、符号、提交 | 申请页缺少必填字段 | 修改已有页面 |
| `<需求编号>-F002` | 管理后台前端 | 文件、符号、提交 | 缺少审核操作与反馈 | 扩展已有列表 |
| `<需求编号>-F002` | 后端服务 | 路由、服务、数据结构、提交 | 需补充状态约束 | 修改业务方法 |

以上为结构示例，不是对实际仓库的分析结论。每个正式设计必须使用真实证据，拟新增文件、接口、函数明确标为“拟新增”；不可读和未核实对象不能当作已存在能力。

代码体现现状，PRD 定义目标；既不能无视代码重新造一套系统，也不能为迎合历史实现而默默缩减需求。

### 6.2 详细设计最低内容

每个仓库按自身规范，至少描述适用内容：

1. 对应需求、输入版本、本仓库范围与非目标。
2. 现有实现、可复用能力与差距。
3. 修改/新增的模块、文件和职责，关键调用或状态流。
4. 接口请求、响应、字段类型、空值、校验、错误语义及调用关系。
5. 前端交互、组件复用、数据获取与状态处理，或后端业务规则与数据访问。
6. 权限及适用的事务、并发、幂等、性能等风险控制。
7. 跨仓库依赖、契约版本、联调方式及实现顺序。
8. 验收映射、测试增量、回归范围和已知未决项。

不要求提前写完整代码，但关键规则和边界不能留给开发猜测。不为套用通用模式而无需求依据地换框架、改目录、加中间件或重构。

## 7. 多仓库协调与唯一来源

仓库分为修改、依赖、参考三类；修改仓库生成自身设计，依赖/参考仓库不默认写入空文件。

- PRD 保留在产品交付位置，各仓库引用同一固定版本，不各维护一份业务需求副本。
- 牵头仓库保存跨仓库问题清单和协调说明，关联各仓库产物。
- 已有共享契约优先沿用其权威位置；新增接口契约原则上由提供方仓库维护，调用方引用明确版本。
- 协调说明记录需求覆盖、仓库职责、共享字段/状态、依赖顺序和未决项，不复制各仓库设计正文。
- 仓库间链接使用仓库身份、相对文件路径及提交/版本引用，不使用另一台电脑上的绝对路径。

多仓库写入可能部分成功。最终清单逐仓库报告成功、失败和未写入项，不能将部分完成说成整体完成。重试前检查现有文件和用户变更，避免覆盖他人修改。

## 8. 文件命名与归档

### 8.1 稳定编号

需求单编号沿用产品正式编号，如 `REQ-2026-001`；条目可使用 `REQ-2026-001-F001`，问题使用 `REQ-2026-001-Q001`。已有条目编号不随意重编。仓库任务编号可使用 `<需求编号>-<repo-id>-T001`。

文件名中的需求编号必须和目录及元信息一致。若来源编号不适合跨平台文件名，先约定稳定的安全映射并保留原始编号，不能静默截断或替换造成冲突。

### 8.2 各修改仓库的设计产物

```text
<代码仓库>/docs/requirements/<需求编号>/
├── <需求编号>-<repo-id>-impact.md
├── <需求编号>-<repo-id>-spec.md
├── <需求编号>-<repo-id>-design.md
├── <需求编号>-<repo-id>-tasks.md
└── <需求编号>-<repo-id>-review.md
```

| 文件 | 责任 |
| --- | --- |
| `impact` | 代码事实、分析依据、需求差距和改动范围 |
| `spec` | 本仓库承担的系统行为、边界和验收映射，不重新定义产品业务 |
| `design` | 可执行的详细实现方案和跨仓库契约引用 |
| `tasks` | 可执行任务、前置依赖、完成标准、验证方法及状态 |
| `review` | 设计自检与真实人工评审，问题和风险分别记录 |

牵头仓库额外保存：

```text
<需求编号>-questions.md       # 澄清阶段先产生，不必等设计准入
<需求编号>-coordination.md    # 跨仓库分工、契约与产物索引
```

澄清阶段不创建空的完整设计包；进入设计后按上述职责输出。小需求如需合并文件，应遵循已确认的仓库规范并保留对应内容及引用，不能自行省略关键交付。

### 8.3 文档元信息

每份仓库研发文档记录需求编号、文档类型、仓库 ID、产品基线引用、分析代码提交、文档版本和状态。示意：

```yaml
---
requirement_id: REQ-2026-001
repo_id: admin-web
document_type: design
stage: engineering
product_version: "1.1"
document_version: "0.1"
status: draft
---
```

产品文件引用、代码提交和本地变更影响填写实际值，可在正文基线表中记录；不得照抄示例版本冒充真实信息。跨仓库文档改用涉及仓库清单和各自基准，不用单个提交代表全部仓库。

### 8.4 版本管理

优先通过各仓库 Git 管理，文件名保持稳定，不使用“最终版2”等后缀。评审记录绑定具体文件版本；尚未提交时标记工作区草案及可核验快照，不虚构提交。

文档生成不自动授权提交、推送或创建 PR。需求或代码基准发生变化时重新分析受影响部分，并更新需要重审/复测的状态。

## 9. 设计自检与人工评审

架构师先自检：

- 目录、文件名和元信息中的需求编号、仓库 ID 一致。
- 每条在范围内的需求有明确责任仓库、规格、设计和验证方式。
- 所有“已存在”代码对象有真实依据，拟新增对象标记明确。
- 每个方案遵循对应仓库规范，差异已说明。
- 跨仓库接口、字段类型、状态及错误处理一致。
- 阻塞问题已关闭并回写，未决问题没有被伪装成已决定。
- 文档真实落盘且链接可定位，部分写入状态如实披露。

随后由产品确认业务解释，仓库负责人确认技术设计，测试按需确认可验证性。实际意见进入评审记录；AI 自检通过不能代替人工评审。

“可开发设计包”的条件：设计范围内阻塞问题已解决、设计与任务可执行、跨仓库依赖已明确，必要设计评审和任务人工评估完成，并确认具体任务版本。未达到条件的包可以交付为草案，但不能标记可开发。可开发表示准备就绪，不代表已经授权执行。

### 9.1 tasks 必须先由人评估

生成的 tasks 默认是草案/待评估，执行状态为未开始。人工检查范围、粒度、仓库归属、依赖、技术可行性、工作量、负责人、排期和验证方式。专家可以给有依据的估算，不编造人员承诺或确定工期。

流程：任务草案 → 人工评估 → 提出意见 → 专家调整 → 人工确认任务基线 → 明确授权开始开发。

意见按任务 ID 和版本记录到 review。调整任务拆分或依赖时更新 tasks；影响方案时同步 design，影响系统行为时同步 spec，改变业务含义时返回产品澄清。拆分/合并保留旧 ID 与新 ID 的对应，不复用废弃 ID。

### 9.2 评审、执行与授权分开

| 维度 | 状态或记录 |
| --- | --- |
| 评审状态 | 草案、待评估、待调整、已确认 |
| 执行状态 | 未开始、进行中、阻塞、待验证、已完成 |
| 开发授权 | 实际授权来源、授权任务范围、针对的版本 |

每项任务分别记录两类状态，文档总状态不能替代逐任务状态。确认记录包含实际确认来源、任务集合及可定位版本；未提交文档可保留已确认快照及内容哈希，不虚构 Git 提交。

专家不能自行标记人工已确认。人工确认任务不等于授权立即开发；同一条消息可以明确完成这两件事，但不能从“方案可以”“继续完善”推断执行授权。

范围、关键方案、依赖或完成标准变化时，受影响任务重新进入待评估，暂停其执行，不继承旧审批。无关且独立任务不必全部重新评估。

## 10. 研发实现与提测衔接

设计阶段结束于人工确认的任务基线，不自动进入代码实现。同一个软件架构师专家可以在明确授权后切换开发执行模式，无需建立重复角色。

### 10.1 执行前检查

读取已确认 tasks、关联 spec/design、PRD 验收和仓库规范，确认授权覆盖当前版本与任务，关键问题已关闭、依赖确实可用。核对当前代码与设计基准的差异、已实现部分和本地用户修改，避免重复开发或覆盖改动。

未评估任务、已失效版本、关键依赖缺失或影响设计的代码变化，先反馈并处理，不用“开始开发”的请求伪造任务已确认记录。

### 10.2 实施与验证

按依赖顺序实施已确认且授权范围内的任务，保留需求/验收映射。发现方案不成立或业务不明确时暂停受影响任务，提出证据和修改建议，必要时重新评估。

执行仓库实际支持的构建、类型检查和适用测试，记录命令、平台、实际结果及代码状态。代码写完但必要验证未执行为待验证；检查失败或依赖阻塞如实记录。约定要求人工代码评审时，获得真实结论后才能满足相应完成标准。

“已完成”仅表示该任务约定完成标准满足，不等于需求整体验收通过或批准发布。例外由有权人员决定并记录风险，不能将未验证改写为通过。

普通开发授权不自动授权任意提交、推送、建 PR、生产数据变更或发布，相关操作仍需符合用户授权和环境权限。

### 10.3 执行记录与提测

tasks 维护逐任务状态、改动及验证证据引用；详细验证/代码评审可使用现有系统或同需求 review。多仓库分别报告，部分完成不代表整体完成。

实现完成时，各仓库补充 `<需求编号>-<repo-id>-handoff.md`，记录实际提交/制品、自测结果、环境准备、已知问题和回归范围。牵头仓库协调一组明确的跨仓库提测版本；设计阶段不得提前填入虚构结果。

## 11. 流程验收场景

| 场景 | 预期行为 |
| --- | --- |
| PRD 关键业务规则缺失 | 先输出具体问题及影响，等待产品补充，不生成完整正式设计 |
| 原型与 PRD 冲突 | 引用冲突位置，要求确认权威业务决定并回写 |
| 仓库文档与代码冲突 | 提供代码证据，由研发核实，不自行将任一方视为绝对正确 |
| 一个仓库无法读取 | 标记未核实和受影响范围，不编造实现，不能宣称整体设计完成 |
| 部分非阻塞信息缺失 | 明确边界后继续不受影响部分，保留问题及状态 |
| 产品已回复但未回写 | 标为已答复待回写，不直接关闭问题 |
| 多仓库共享接口不一致 | 阻塞相关设计交付，统一契约后重新核查 |
| 需求明确且代码证据完整 | 按仓库规范设计并分别归档，不重复询问已确认事项 |
| 设计过程中 PRD 升版 | 对比变化，重评影响并更新输入基线和评审状态 |
| 多仓库仅部分文件写入成功 | 逐项报告，不声称完整交付；安全补齐后再核对 |
| tasks 刚生成 | 标记草案/待评估、执行未开始，等待人工意见 |
| 用户要求继续完善任务 | 调整文档，不推断确认或开发授权 |
| 任务已确认但未授权开发 | 保持未开始，交付基线并等待明确指令 |
| 人工调整任务导致方案变化 | 同步 spec/design，重新评估受影响任务 |
| 要求执行未经评估的 tasks | 请求先完成评估，不伪造已确认状态 |
| 代码写完但测试未执行 | 标记待验证，披露缺口，不标已完成 |
