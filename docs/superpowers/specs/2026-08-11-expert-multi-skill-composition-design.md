# 专家创建会话多技能组合设计

## 1. 背景

当前“创建专家”会话会固定激活 `expert-manager`，但 Composer 将 Creator 会话视为完全锁定状态，导致“+”菜单隐藏“技能”入口，动态技能插入逻辑也拒绝 Creator 会话。后端同时只解析位于整条消息开头的单个斜杠技能，无法可靠表达多个技能。

本设计参考 WorkBuddy 的输入框交互：固定管理能力与用户选择的业务能力同时以技能胶囊展示。WorkBuddy 的视觉行为只决定选择方式；最终数据和打包方式由可移植性、可信状态、最小权限及原子注册等系统约束推导。

## 2. 目标

1. 创建专家会话继续固定激活官方 `expert-manager`。
2. 用户可从 Composer 的“+ → 技能”菜单选择多个业务技能。
3. 已选技能以可删除、可去重的胶囊展示。
4. 选择结果通过结构化字段传给后端，不依赖输入文本解析。
5. `expert-manager` 使用现有脚本流程，把通过安全校验的技能快照到新专家包，使专家可独立安装和分享。
6. 任一技能处理失败时禁止注册残缺专家。
7. 普通聊天、技能创建会话和现有斜杠命令行为不受影响。

## 3. 非目标

1. 不把 MCP 连接器复制进专家包。
2. 不把 `expert-manager` 本身复制进新专家包。
3. 不实现远程技能依赖解析、自动升级或依赖下载。
4. 不允许专家包引用项目配置目录之外的绝对路径。
5. 不将输入框中的可编辑文本作为技能选择的唯一事实来源。

## 4. 第一性原理与设计推导

### 4.1 可信状态

contenteditable 中的文本可以被删除、粘贴或重排，因此技能选择必须保存为独立的结构化状态。消息发送载荷增加 `selectedSkillNames: string[]`，后端重新校验，前端状态只负责交互展示。

### 4.2 可移植性

新专家在另一台机器安装后仍需具备相同能力。最终 `plugin.json.skills` 只能声明包内相对路径，例如 `./skills/report-writer`；Agent MD 的 `skills` frontmatter 使用对应技能名。不能只记录创建机器上的技能名称或绝对路径。

### 4.3 控制面与业务面分离

`expert-manager` 是创建流程的控制面能力，由会话类别在后端强制注入。用户选择的其他技能是新专家的业务能力。两者必须分开处理：前者固定显示且不可移除，后者可多选、可删除，并在通过安全与完整性校验后进入最终包。

### 4.4 最小权限与供应链边界

后端只接受当前技能注册表中已启用、可读取且名称匹配的技能。快照过程拒绝路径越界、符号链接、循环链接、缺少 `SKILL.md`、非法名称及同名内容冲突。目标路径固定在当前专家目录的 `skills/` 下。

### 4.5 原子可见性

技能快照、专家内容生成和完整校验均成功后，才能调用注册脚本写入 `marketplace.json`。失败产物可以留在未注册草稿目录供用户修复，但不能出现在“我的专家”中。

## 5. 交互设计

### 5.1 “+”菜单

创建专家会话中的菜单顺序为：

1. 添加文件
2. 技能
3. 专家
4. 连接器

Creator 的固定模式仍不可修改，但 `modeLocked` 不再连带隐藏技能入口。技能子菜单沿用现有搜索、加载、键盘导航和错误提示。

### 5.2 技能胶囊

- `expert-manager`：固定胶囊，带锁定语义，不显示删除按钮。
- 业务技能：选择后追加为胶囊，显示技能名称和删除按钮。
- 重复选择：保持原顺序，不重复添加。
- 已选技能：在子菜单中显示选中状态；再次点击不产生副本。
- 忙碌或发送中：禁止改变技能选择。
- 会话切换：每个会话拥有独立选择状态；返回会话后恢复。

输入正文只保留用户描述。技能胶囊不需要伪装成正文中的多个斜杠命令，避免把 UI 表达和协议耦合。

## 6. 状态与数据契约

### 6.1 Renderer 状态

Composer 为当前会话维护：

```ts
type ComposerSkillSelection = {
  conversationId: string;
  skillNames: string[];
};
```

创建会话 bootstrap 只负责预填专家需求模板；固定 `expert-manager` 由会话类型渲染，不进入可编辑技能数组。

为避免切换会话丢失，选择状态存放在全局 store，以 `conversationId` 为键。会话删除时同步清理。

### 6.2 Prompt 请求

`POST /api/prompt`、Electron IPC 与 Provider PromptOptions 增加：

```ts
selectedSkillNames?: string[];
```

约束：

- 仅 `expert_creator` 接受多个业务技能。
- 去重后最多选择 8 个技能；技能快照合计最多 32 MiB、2048 个普通文件。
- 不允许客户端把 `expert-manager` 放入该数组。
- 普通会话缺省为空，不改变现有行为。

### 6.3 后端解析结果

后端只负责将名称解析为受信任的技能描述，并把结果交给已有的 `expert-manager` 工作流：

```ts
type ResolvedExpertSkill = {
  name: string;
  root: string;
  body: string;
  source: "builtin" | "user";
  revision: string;
};
```

`root` 和完整文件树只供受保护工具使用，不直接拼入用户可编辑文本。系统上下文向 `expert-manager` 提供经过转义和限长的技能清单、来源与精确快照规则。后端不初始化专家目录、不修改专家 manifest，也不注册或打包专家，避免与 `expert-manager/scripts` 形成第二套生命周期实现。

## 7. 专家包物化规则

目标结构：

```text
<expert>/
├── .picoddy-plugin/plugin.json
├── agents/<agent>.md
└── skills/
    ├── skill-a/
    │   ├── SKILL.md
    │   └── ...
    └── skill-b/
        ├── SKILL.md
        └── ...
```

生命周期继续由 `expert-manager` 及其现有脚本驱动，处理顺序为：

1. 后端解析并冻结本次选择的技能清单。
2. `expert-manager` 调用现有 `init_expert.py` 初始化专家草稿目录。
3. `expert-manager` 通过已有文件工具读取已解析的技能根，并把每个允许打包的技能物化为包内快照。
4. `expert-manager` 生成专家内容，同时更新 `plugin.json.skills` 和主 Agent MD 的 `skills` frontmatter。
5. `expert-manager` 依次调用现有 `validate_expert.py`、`register_expert.py --session-id` 和 `package_expert.py`。

不新增后端初始化、注册或打包服务。为覆盖多技能场景，只增强现有 `validate_expert.py` 的技能目录安全与声明一致性检查；`init_expert.py`、`register_expert.py`、`package_expert.py` 继续保持各自现有职责。

可打包技能必须来自系统已注册的内置或用户技能根目录、处于启用状态、包含普通文件 `SKILL.md`，并且完整目录树不含符号链接或越界路径。快照保留 `SKILL.md`、`scripts/`、`references/`、`templates/` 和其他普通文件；忽略 `.DS_Store` 等系统元数据。所有复制目标必须位于新专家的 `skills/` 目录，每个快照记录源类型和内容 SHA-256，供诊断与复现使用。

## 8. 错误处理

- 技能已禁用或不存在：发送前提示用户重新选择。
- 技能源目录不可访问：阻止创建，不降级为名称引用。
- 非法目录、符号链接或越界：返回稳定安全错误并记录不含技能正文的诊断事件。
- 同名不同内容：报告冲突技能名，要求用户移除其中一个。
- 快照中途失败：`expert-manager` 不得调用现有 `register_expert.py`，因此不修改 `marketplace.json`。
- 前端刷新失败：保留已选择名称并标记不可用，用户删除或重新加载后才能发送。

## 9. 测试与验收

### 9.1 单元测试

- 创建专家模式保留技能菜单而继续锁定模式。
- 多技能选择保持顺序、去重、删除和按会话隔离。
- Prompt 请求完整传递 `selectedSkillNames`。
- 后端拒绝 `expert-manager`、禁用技能、未知技能和超限选择，并把合法技能根传给 `expert-manager` 上下文。
- 快照拒绝越界和符号链接，保留合法技能文件。
- 生成后的两个 manifest 声明与磁盘目录一致。
- 现有脚本执行顺序保持 `init → validate → register → package`；初始化、技能物化或校验失败时不会注册专家。打包属于注册后的分发产物生成，失败时保留已经校验并注册的专家，但必须明确报告打包失败，不能声称分享包已经生成。

### 9.2 交互验收

1. 进入“我的专家 → 创建专家”。
2. 输入框显示不可删除的 `expert-manager`。
3. 打开“+”菜单可以看到“技能”。
4. 连续选择两个技能，输入框显示两个可删除胶囊。
5. 重复选择不会新增胶囊。
6. 删除其中一个后发送，后端仅收到剩余技能。
7. 创建完成后的专家包只包含最终选择的技能，并能通过校验、注册和打包。

## 10. 兼容性

普通会话继续支持原有斜杠技能文本和单次技能选择；本次结构化多选仅在 `expert_creator` 启用。现有专家包没有新增必填字段，未选择业务技能时仍可创建不含 `skills` 的专家。
