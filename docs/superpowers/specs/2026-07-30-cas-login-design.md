# Pi-a CAS 登录接入设计

## 背景

当前桌面客户端没有统一的登录认证门禁，启动后会直接进入主界面，后端 API 也能被直接调用。用户希望采用类似 Codex 客户端的方式：

- 启动时先检查登录态。
- 未登录时显示一个专门页面，只保留登录按钮。
- 点击登录后用系统原生浏览器跳转到 CAS。
- CAS 登录成功后，客户端重新获得登录态并进入主界面。

已确认的认证入口为：

```text
https://sso.example.com:8443/cas/login?service=xxx
```

## 目标

- 启动时先做鉴权检查。
- 未登录时前端只展示登录页，不渲染主工作台。
- 登录按钮调用系统默认浏览器打开 CAS。
- 使用本机回调完成登录结果落地。
- 登录态持久化，重启后仍可直接进入主界面。
- 所有 `/api/*` 业务接口都受登录态保护。

## 非目标

- 不改造 CAS 服务端。
- 不做 SSO 多账号切换。
- 不做复杂的单点登出联动。
- 不引入新的第三方认证协议。

## 方案

采用“本机回调 + 本地会话”模型。

### 登录流程

1. 客户端启动后先请求 `/api/auth/session`。
2. 如果本地会话存在且未过期，返回 `authenticated`，前端进入主界面。
3. 如果未登录，前端展示登录页。
4. 用户点击登录按钮，后端生成一次性 `state`，拼出 CAS 登录地址并用系统浏览器打开。
5. CAS 登录完成后回跳到本机 `http://127.0.0.1:<port>/api/auth/callback?ticket=...&state=...`。
6. 后端使用 CAS `serviceValidate` 校验 `ticket`。
7. 校验成功后写入本地 `auth_sessions`，前端轮询或再次请求 `/api/auth/session` 后进入主界面。

### service 设计

`service` 使用当前客户端本机地址，固定到同一个回调入口，保证 CAS 校验时服务地址一致。

建议形式：

```text
http://127.0.0.1:<port>/api/auth/callback
```

如果运行环境不允许回跳到 `localhost`，再切换为可注册的自定义协议方案，但默认先采用本机回调。

### 登录态模型

数据库中的 `auth_sessions` 只保存客户端自己的会话，不保存 CAS 的一次性 `ticket`。

建议字段语义：

- `id`：本地会话 ID。
- `user_id`：CAS 返回的用户名或主体 ID。
- `nick`：展示名。
- `avatar`：可选头像。
- `access_token`：这里存本地会话标识或签名 token，不直接复用 CAS ticket。
- `refresh_token`：预留字段，当前可为空。
- `logged_in_at`：登录时间。
- `expires_at`：过期时间。

## 组件划分

### 后端

新增一个专门的 CAS 认证模块，负责：

- 构造登录 URL。
- 打开系统浏览器。
- 处理回调。
- 校验 ticket。
- 写入和读取本地登录态。

`application.ts` 负责：

- 在 `/api/*` 入口处做认证拦截。
- 提供 `/api/auth/session`、`/api/auth/login`、`/api/auth/callback`、`/api/auth/logout`。
- 在未登录时仍允许访问认证相关接口和静态登录页。

### 前端

`App.tsx` 启动时先调用 session 接口。

未登录时只渲染一个登录页，页面包含：

- 产品标题或简短说明。
- 登录按钮。
- 登录中的加载态。
- 登录失败后的错误提示。

登录成功后自动切回主工作台。

## 安全约束

- `state` 必须是一次性随机值，并和浏览器跳转绑定。
- 回调时必须校验 `state`，避免被任意外部 URL 伪造。
- CAS ticket 必须只用一次，校验成功后立即换成本地会话。
- 本地会话应设置过期时间，避免永久登录。
- `/api/*` 的业务接口要统一检查登录态，不能只靠前端隐藏页面。

## 验证策略

- 单测覆盖登录 URL 生成、回调校验、会话过期、无登录态拒绝业务 API。
- 前端测试覆盖未登录页、登录按钮、登录态切换。
- 集成测试覆盖：
  - 未登录启动进入登录页。
  - 登录后回到主界面。
  - 直接访问业务 API 被拒绝。

## 迁移策略

先接入登录门禁，再把原有业务接口保持原样串起来。

这样可以把风险收敛到三个点：

- 认证模块是否能成功回跳。
- 登录态是否能稳定持久化。
- 未登录拦截是否误伤现有业务。
