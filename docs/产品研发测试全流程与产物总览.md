# 产品—研发—测试全流程与产物总览

日期：2026-09-10  
版本：0.4  
状态：产品专家执行与架构师分仓库设计方向已确认；详细流程待评审

## 一、文档目的与范围

本文根据已有讨论，统一产品、研发、测试三个阶段的流程、职责、交付物与交接条件，作为后续分别细化设计的基础。

本文是目标流程方案，不代表客户端已实现这些能力，也不代表全部流程细节已通过审批。已确认第一阶段使用产品专家执行流程和生成产物；研发设计由软件架构师先审查澄清需求，再结合真实代码按仓库规范设计并分别归档。具体页面、数据库、接口、工作流引擎或自动调度的实现暂不设计。

第一版以本地文档和文件交付为基础，不接入钉钉。先让每个阶段能独立完成交付，再设计阶段之间的自动串联。

## 二、整体定位

采用需求与规范驱动交付（SDD）的思路：先明确产品需求及验收标准，再形成研发规格、设计和任务，最后通过测试证据确认交付结果。

核心不是让 AI 连续生成几份 Markdown，而是让需求、原型、代码和测试之间有明确对应关系，并能随着变更保持一致。本文使用的文件名是本方案的约定，不意味着 SDD 只有一种固定文档格式。

```text
原始需求收集
    ↓
需求澄清与范围确定
    ↓
PRD + 可交互原型
    ↓
产品评审与版本确认
    ↓
研发规格 + 技术设计 + 任务拆解
    ↓
任务人工评估 → 调整 → 确认任务基线
    ↓
明确开发授权 → 代码实现 + 自测 + 代码评审
    ↓
提测交接
    ↓
测试用例 + 测试执行 + 缺陷闭环
    ↓
业务验收与交付确认
```

三个阶段是主要责任划分，不意味着完全串行。研发可提前参与可行性评审，测试可提前检查需求是否可验证。评审发现问题或需求变更时，返回受影响的环节修订。

### 阶段职责

| 阶段 | 核心问题 | 主要负责人 | 核心交付物 |
| --- | --- | --- | --- |
| 产品 | 为什么做、为谁做、做什么、怎样验收 | 产品专家执行；产品经理决策与确认 | `prd.md`、交互原型、产品评审结论 |
| 研发 | 需求是否清晰可行、如何基于现有代码实现及验证 | 软件架构师负责设计；产品与研发确认；开发人员实现 | 需求问题清单、按需求编号和仓库命名的规格/设计/任务、代码、自测与提测说明 |
| 测试 | 是否符合需求、是否存在缺陷、是否满足交付条件 | 测试负责人及测试人员 | 测试计划、用例、适用的自动化脚本、缺陷记录、测试报告 |

AI 可以辅助整理、生成、检查和执行，但不能将自己的检查结果当作人的审批结果。

## 三、产品阶段

### 已确认决策：使用产品专家执行

第一阶段由现有“产品专家”（`product-design--product-management` 专家包）作为统一执行入口，负责从原始需求整理到产品交付包生成及修订。不是只让专家写一份 PRD，也不要求产品经理逐个手动调用不同能力来拼接产物。

产品经理提供需求、补充业务信息并作出决定；产品专家组织工作、生成文件、执行可用的检查、整理评审意见。专家不代替产品经理、业务方或前端负责人批准需求与规范。

采用已补充的产品专家能力组合：

| 能力 | 在本阶段的职责 |
| --- | --- |
| `product-delivery` | 组织需求澄清、文档与原型交付、验证、评审修订和版本一致性 |
| `feature-spec` | 形成 PRD 的业务定义、需求结构、范围和验收条件 |
| `frontend` | 提供项目样式、页面模式、组件值契约、交互规范及原型参考 |
| 其他产品能力 | 仅在需求确有需要时辅助用户研究、竞品分析、指标等，不强制全部执行 |

这里描述的是产品专家的目标执行方式，不是在本次文档编辑中调用上述能力。专家源包已补充相关能力，不等于客户端已加载，也不等于完整业务场景已验证；客户端加载和实际生成效果需在后续落地时核验。

### 3.1 输入

可以从一句话想法开始，也可以输入：

- 用户反馈、访谈记录、业务问题。
- 已有需求文档、截图、历史原型。
- 当前系统能力和业务规则。
- 项目前端组件、样式及交互规范。
- 业务目标、范围限制和时间约束。

连接器只用于补充上下文，不作为工作前提。没有 MCP，也应能基于本地文件和用户描述完成产品交付。

启动时，产品专家至少接收需求描述和可用上下文，并确定交付位置。需求名称/标识、目标系统、前端规范、交付版本及已有产物可由用户提供，也可从项目中识别；不能可靠确定时列为待确认信息，不编造业务结论。首次交付与对已有版本的修订需要区分。

### 3.2 工作流程

| 步骤 | 产品专家执行的工作 | 人员参与及确认 | 结果 |
| --- | --- | --- | --- |
| 需求收集 | 读取描述和资料，整理来源、问题及证据，合并重复反馈 | 提供原始信息，纠正背景理解 | 需求来源记录 |
| 需求澄清 | 梳理用户、场景、范围、规则和约束，提出关键问题，区分假设与事实 | 产品经理或业务方确认关键业务决定 | 明确需求与待确认项 |
| 产品定义 | 生成 PRD，分配稳定需求/验收编号，描述页面、字段、权限和验收条件 | 确认业务含义与本次范围 | `prd.md` 草案 |
| 原型设计 | 依据 PRD 和前端规范生成可操作文件，标明模拟数据与规范差异 | 确认业务流程和交互；前端负责人确认规范差异 | 交互原型 |
| 一致性与交互检查 | 核对需求、原型和验收映射；实际执行具备条件的交互检查 | 对未验证项安排人工检查或补齐条件 | 自检结果、证据与问题清单 |
| 评审修订 | 整理真实评审意见，同步修订 PRD 与原型，记录版本影响及复测结果 | 产品、业务、研发、测试等相关人员按职责评审 | 更新的产物与 `review.md` |
| 交付整理 | 核对文件和版本，输出路径、打开方法、未决项及交接状态 | 产品经理确认交付基线；接收方确认阻塞项处理情况 | 可定位的产品交付包 |

不确定内容应区分为假设、待确认和已决定，不能自动补成事实。已明确的信息不重复追问，阻塞性问题优先澄清。

### 3.3 最终产物

| 产物 | 内容与要求 |
| --- | --- |
| `prd.md` | 背景、目标、范围、业务流程、需求编号、页面、字段、权限、验收条件、风险及未决项 |
| `prototype/index.html` 及资源 | 默认可离线打开，能演示范围内的主要交互，使用模拟数据 |
| `review.md` | 产品评审意见、前端规范确认、问题处理情况和最终结论；与 AI 自检分开记录 |
| 钉钉文档链接及版本 | 后续接入时提供；第一版不接入，链接与版本留空并明确记录“不接入” |

原始反馈较多时，可额外保留 `intake.md`；简单需求直接在 PRD 中记录来源，不强制增加文件。

如选择托管原型，可用固定版本链接替代原型文件，但必须记录版本标识和访问限制，不能使用无法确定评审对象的持续变化链接。

产品专家对完整产品阶段请求必须实际生成上述文件，不能只输出说明、代码片段或“建议创建”的目录。默认交付要求如下：

- **PRD**：记录需求/交付标识、版本、状态、需求来源、稳定的 REQ/AC 编号、原型入口和评审记录引用。
- **原型**：交付 `prototype/index.html` 和必要的本地资源，显示对应交付版本，说明打开方法、模拟数据及未实现项。
- **评审记录**：分别记录 AI 自检、人工产品评审、前端规范确认；检查项包括步骤、预期、实际结果和证据。未执行写“未验证”，未收到审批写“待评审/待确认”。
- **交付说明**：在最终回复中列出真实文件位置、版本、当前状态和阻塞问题，不强制新增第四份本地说明文件。
- **钉钉**：第一版不创建在线文档，不把缺少钉钉链接认定为交付失败。

默认逻辑目录为 `product/<需求标识>/<交付版本>/`，用户或项目已有目录约定优先。与第八节需求级目录组织择一使用，不重复存放两套权威产物。已确认版本保留，修订另建新版本或按项目版本管理规则留存，不能静默覆盖评审对象。

### 3.4 交互原型要求

原型需要参考对应项目的前端组件和交互规范，而不仅是颜色相似。

重点包含：

- 布局、表格、筛选区、表单、弹窗等页面模式。
- 组件的单选/多选、显示值、实际值及字段类型。
- 查询、重置、跳转、返回、保存、取消等适用行为。
- 加载、空数据、失败、无权限等适用状态。
- 保存成功后的页面变化，失败后的输入保留。

原型中的模拟保存、模拟权限、模拟上传，不代表生产功能已经实现。可点击控件应有真实可观察的演示效果，未实现项必须明确标注；说明数据保存、刷新与重置行为。

默认交付独立 HTML 与相对路径资源，不依赖生产 API、CDN 或开发环境。在项目支持的平台上检查可打开性与资源加载，不依赖某台电脑的绝对路径。

截至本次讨论，提供的前端规范为 `0.1.0-draft`，生成预览时应保留“待前端确认”标记，不自行视为已批准标准。新增组件或偏离既有规范的交互需记录差异。

### 3.5 进入研发的条件

- 本次范围及关键业务规则已确认。
- 关键需求有明确、可验证的验收条件。
- PRD 与原型对应且交付版本一致。
- 产品评审有真实结论。
- 阻塞性问题已解决；其余问题有明确影响和处理安排。

产品专家应分别报告“文件是否交付”“检查是否执行”“人工是否确认”“是否满足研发交接条件”，不能用单一的“已完成”掩盖缺口。

### 3.6 评审反馈与修订闭环

产品经理可以在同一需求上下文中继续提交评审意见。产品专家应定位所依据的交付版本，识别受影响的需求、验收项和原型页面，然后同步修订文件及评审记录。

- 业务规则变化：更新 PRD、相关原型行为和验收条件，标记需重新确认的结论。
- 仅原型表现变化：记录是否影响业务含义和前端规范，并执行适用复测。
- 信息不足：记录问题、影响、待确认角色及阻塞性；非阻塞部分可继续生成草案。
- 工具不足或检查失败：如实记录未验证项或缺陷，不使用参考原型的历史检查结果替代本次验证。

“待评审”的产品包可以用于讨论，但不能伪装为已确认的研发输入。规范仍为草案时，明确其风险是否阻塞交接及由谁确认。

### 3.7 本阶段边界与待细化事项

本次确认的是执行主体及交付方式：由产品专家完成产品阶段流程和产物。完整交付请求默认包括 PRD、原型和评审记录；用户明确只请求其中一项时尊重范围，不强制执行全流程。

第一版不自动生成研发 `spec.md`、`design.md`、`tasks.md`，不执行生产代码开发，不把原型验证当作正式系统测试，也不自动写入 TAPD 或钉钉。

以下事项仍留待详细设计：

- 产品专家在客户端中的选择/绑定方式，以及需求输入弹窗的具体字段。
- 项目资料、前端规范和可选连接器的配置与权限。
- 产物预览、评审意见收集、版本选择与状态展示。
- 专家加载检查、真实业务样例验证与产品阶段功能验收。

不因确认使用产品专家，就推定这些平台功能已经具备或已被批准实现。

## 四、研发阶段

详细流程见[研发阶段需求澄清与多仓库设计流程](./研发阶段需求澄清与多仓库设计流程.md)。以下文档简称表示产物类型，实际研发 Markdown 必须按 `<需求编号>-<repo-id>-<类型>.md` 命名，保存在所属代码仓库。

### 已确认决策：先澄清，再基于代码分仓库设计

软件架构师接收产品交付包并关联相关代码仓库后，先检查需求是否完整、清晰、合理及可验证。结合代码和项目约束，对缺失、歧义、冲突提出有证据的问题：业务问题交产品补充，技术问题交研发核实。

这一阶段可以输出问题清单、代码证据和方案建议，但不批量生成正式设计。产品回复需回写到 PRD、原型、验收条件或受控补充记录，并复核后关闭问题；不能以聊天里的一句回复代替完整闭环。

阻塞问题未解决前，不进入受影响部分的正式设计；独立且已明确的部分可以生成标明范围的草案，不能把整体标记为可开发。不得将 AI 假设当作产品决定。

### 4.1 输入

研发人员选择的不是一份持续变化、没有版本的文档，而是一个明确的产品交付版本：

- 已确认的 `prd.md`。
- 对应版本的原型。
- 产品评审结论。
- 现有代码、架构约束、开发及测试规范。

每个仓库提前准备 `docs/development/design-guidelines.md` 作为设计规范入口，引用项目上下文、架构、接口/组件约定与验证要求；已有项目文档优先复用。登记仓库 ID、来源、本地目录、基准提交和修改/依赖/参考类型。

老项目先识别当前实现、项目规范、构建和测试方式，形成经研发核实的最小基线，再针对本需求补充规格；不要求先将整个历史项目重写为 SDD 文档。产品定义目标行为，代码提供现状证据，两者冲突时反馈确认，不能静默改需求或照搬旧行为。

### 4.2 三份核心文档的区别

| 文档 | 回答的问题 | 主要内容 |
| --- | --- | --- |
| `spec.md` | 本次系统必须表现成什么样 | 系统行为、输入输出、边界、异常、适用的兼容要求及验收对应关系 |
| `design.md` | 用什么技术方案实现 | 模块划分、接口、数据模型、权限、依赖、适用的迁移方案及风险 |
| `tasks.md` | 按什么顺序完成 | 可执行任务、仓库归属、依赖、完成标准、验证方式及状态 |

`spec.md` 不是简单重写 PRD；它需要把产品表达转成明确的系统行为，但不能自行改变产品需求。发现矛盾或缺口时应反馈产品确认。

`design.md` 不重复需求全文，而是说明实现决策。兼容、数据迁移等内容仅在目标项目规范允许且本次确有需要时设计，不无条件增加。

`tasks.md` 不能只有“开发前端、开发后端、测试”这类粗粒度事项，需要能独立执行和判断完成。

### 4.3 工作流程

| 步骤 | 主要工作 | 结果 |
| --- | --- | --- |
| 需求审查 | 检查范围、业务规则、原型一致性和验收条件 | 初步问题清单 |
| 现状分析 | 理解已有实现、可复用能力和影响范围 | 影响分析 |
| 澄清与补充 | 对照代码提出问题，产品/研发答复并回写、复核 | 已闭环问题及未决项 |
| 设计准入 | 确认输入基线、仓库职责和阻塞问题处理情况 | 可设计范围 |
| 规格确认 | 将需求转为系统行为与约束 | `spec.md` |
| 技术设计 | 设计接口、数据、模块和跨系统协作 | `design.md` |
| 任务拆解 | 明确任务依赖及验证方法 | `tasks.md` |
| 研发评审 | 确认可行性、适用的兼容性和风险 | 研发评审记录 |
| 任务人工评估 | 人评估范围、粒度、依赖、工作量和验证；专家调整并同步相关设计 | 已确认的任务基线 |
| 开发授权 | 明确执行任务范围及版本，不能由设计或任务确认自动推断 | 实际授权记录 |
| 开发与自测 | 按任务实现，执行适用检查与测试 | 代码、测试及执行结果 |
| 代码评审与提测 | 检查实现、准备可定位的构建版本 | 提测交付包 |

### 4.4 最终产物

设计前，牵头仓库先保存 `<需求编号>-questions.md`，不创建一套空的设计文档。进入设计后，各修改仓库保存以下产物；跨仓库分工与索引存为牵头仓库的 `<需求编号>-coordination.md`。

- `<需求编号>-<repo-id>-impact.md`：代码证据与改动范围。
- `<需求编号>-<repo-id>-spec.md`：本仓库目标行为与验收映射。
- `<需求编号>-<repo-id>-design.md`：详细实现方案。
- `<需求编号>-<repo-id>-tasks.md`：可执行任务与依赖。
- `<需求编号>-<repo-id>-review.md`：自检与真实人工评审。

上述为“可开发设计包”，需要相应阻塞问题解决、必要设计评审与任务人工评估完成。tasks 默认待评估，不是执行指令；评审状态与执行状态分别维护，确认任务也不自动授权开发。重要变更需重新评估受影响任务。明确授权后，同一专家可按已确认任务编写代码并验证；未验证不能标任务完成。进入实现后再补充：

- 代码变更及关联的提交、PR。
- 开发侧测试代码和真实执行结果。
- 研发设计与代码评审记录或可定位链接。
- `<需求编号>-<repo-id>-handoff.md`：提测说明。

按需增加接口契约、数据库变更文件和部署配置，不要求所有需求都生成空文件。

提测说明至少包含：

- 对应需求及产品版本。
- 本次实现范围与未实现项。
- 各仓库提交、构建或制品版本。
- 测试环境、配置、数据准备方式。
- 自测结果、已知问题和重点回归范围。

### 4.5 进入正式测试的条件

代码已实现且必要评审完成，已有可测试的明确版本；相关系统依赖、环境、数据和访问方式可用。

“代码写完”不等于“可以提测”。研发自测只记录实际执行结果，未执行项应明确披露。

## 五、测试阶段

### 5.1 输入

测试不只读取 PRD，还需要：

- PRD、原型及产品评审结论。
- `spec.md`、相关技术设计和接口契约。
- 研发提测说明。
- 明确的代码/构建版本、环境和已知问题。

### 5.2 工作流程

| 步骤 | 主要工作 | 结果 |
| --- | --- | --- |
| 测试分析 | 识别范围、风险、变更影响和验收覆盖 | 测试计划 |
| 用例设计 | 覆盖正常、异常、边界、权限和回归 | 测试用例 |
| 用例评审 | 检查遗漏与预期结果是否明确 | 用例评审记录 |
| 自动化准备 | 将适合自动化的用例转为可执行脚本 | 测试脚本 |
| 执行测试 | 对指定版本实际执行并收集证据 | 执行记录 |
| 缺陷闭环 | 发现、定位、修复、复测和回归 | 缺陷记录 |
| 验收总结 | 汇总覆盖、风险和未解决问题 | 测试报告及验收结论 |

### 5.3 最终产物

| 产物 | 内容 |
| --- | --- |
| `test-plan.md` | 范围、策略、风险、环境及进入/退出条件 |
| `test-cases.md` | 用例编号、关联需求、前置条件、步骤、预期结果和优先级 |
| 自动化测试脚本 | 适合自动执行的接口、组件或端到端测试 |
| `test-report.md` | 测试版本、环境、实际结果、证据、覆盖及剩余风险 |
| 缺陷记录或固定链接 | 复现步骤、影响版本、严重程度、处理及复测状态 |
| `acceptance.md` | 业务验收结论及有权确认人员的实际意见 |

用例评审意见可保存在测试用例文档或既有评审系统中。小需求可以将测试计划和用例合并，业务验收也可作为测试报告的独立章节。

可测试的 Markdown 是结构化测试说明，不等于可执行自动化脚本；生成了用例，也不等于执行了测试。产品原型验证也不能替代对研发实现的测试。

### 5.4 完成条件

- 对约定范围执行了必要测试，并有真实结果。
- 阻塞性交付问题已解决。
- 未解决风险已明确披露，并由相应负责人决定是否接受。
- 测试结论和业务验收分别记录。

测试通过不自动等于批准上线；发布审批和部署可作为后续独立环节。

## 六、一个需求涉及多个仓库时

采用“一个业务需求基线，多个仓库实现单元”。

| 层级 | 管理内容 |
| --- | --- |
| 需求层 | 统一 PRD、原型、验收标准和需求版本 |
| 跨仓库设计层 | 系统分工、共享接口、依赖顺序和联调要求 |
| 仓库层 | 各仓库实现设计、任务、代码、测试与提交版本 |
| 整体验证层 | 跨系统业务流程、接口兼容及整体验收 |

例如同一需求涉及后台前端、业务服务和权限服务：

- 产品只维护一份需求定义。
- 研发明确每个需求点由哪些仓库实现。
- 仓库内分别维护任务和代码变更。
- 提测时记录三个仓库组成的版本集合。
- 测试既验证单仓库能力，也验证完整业务链路。

不能因为其中一个仓库完成，就把整个需求标记为完成。不同系统可以关联不同前端规范，不能将某个后台组件标准直接强加给所有端。

研发产物分别落在对应代码仓库，仓库登记与归档规则见[研发详细流程](./研发阶段需求澄清与多仓库设计流程.md)。共享需求引用同一产品版本，接口契约引用权威提供方的明确版本，牵头仓库保存协调记录；不复制维护多套共享规则。客户端配置和任务分发实现仍待后续设计。

## 七、统一编号、版本与变更规则

### 7.1 可追溯关系

建议保留以下关系：

```text
需求 REQ → 验收条件 AC → 研发任务 TASK → 代码变更 → 测试用例 TC → 执行结果/缺陷
```

允许一对多、多对多，不强求一个需求只对应一个任务或用例。需求修订时保留稳定编号，不因调整顺序就重编全部编号。

### 7.2 区分不同版本

- 产品版本：确认的是哪版需求和原型。
- 研发版本：依据哪版需求、实现到哪个提交。
- 测试版本：实际测试的是哪个构建及环境。
- 验收版本：最终确认的是哪组交付物。

不要将这些全部简化成一个无法定位实际代码的“v1”。产品交付包内部的 PRD、原型、评审对象应保持对应，但不要求产品版本号等于应用版本号。

### 7.3 变更闭环

需求发生变化后：

1. 记录变更内容和原因。
2. 分析受影响的原型、设计、仓库、任务和用例。
3. 更新相关产物并标记需要重审、复测的部分。
4. 根据影响范围重新确认。
5. 保存旧版本及其历史结论。

旧版评审或测试通过，不自动适用于新版。

## 八、建议的产物组织方式

已确认研发设计产物分别保存在所属代码仓库，不再将下列阶段目录理解为全部集中存放。产品包沿用产品阶段约定，测试归档的详细方案后续确认：

```text
产品交付位置/<需求编号>/<产品版本>/
├── prd.md
├── prototype/index.html
└── review.md

每个修改仓库/docs/requirements/<需求编号>/
├── <需求编号>-<repo-id>-impact.md
├── <需求编号>-<repo-id>-spec.md
├── <需求编号>-<repo-id>-design.md
├── <需求编号>-<repo-id>-tasks.md
└── <需求编号>-<repo-id>-review.md

牵头仓库的同一需求目录额外保存：
├── <需求编号>-questions.md
└── <需求编号>-coordination.md
```

研发文件名、需求目录与元信息中的编号必须一致，仓库级文件还需匹配稳定的仓库 ID。仅依赖或参考的仓库不默认写入空产物。研发文档具体内容、版本规则和归档检查以研发详细流程为准；产品专家当前的文件命名不在本次自动更改。

生产代码和可维护的自动化测试通常保留在所属代码仓库，通过引用关联，不需要复制进文档目录。文档采用相对链接或可定位的版本引用，避免依赖个人电脑路径。

## 九、专家、技能与连接器的定位

产品阶段已确认使用产品专家；研发设计已确认使用软件架构师，需补充需求澄清、代码证据、仓库规范和分仓库归档约束；开发执行及测试的具体专家配置仍待细化。此处统一各元素职责，不提前设计自动串联：

| 元素 | 定位 |
| --- | --- |
| 专家 | 承担角色责任，例如产品定义、研发设计、测试分析 |
| 技能 | 提供可复用的方法和产物规范，例如 PRD、前端原型、测试用例 |
| MCP 连接器 | 获取或写入外部系统数据，例如需求平台、设计工具、代码平台 |
| 阶段流程 | 管理输入、产物、状态、评审和交接条件 |
| 人员 | 作出业务决策、审批及风险接受决定 |

关联了专家、技能和连接器，不代表流程就已经具备自动推进、版本管理或审批能力；这些应在后续平台设计中单独明确。外部写入需要对应授权，不能因连接器可用就自动发布文档或修改事项。

此前提出的“类似新建项目弹窗，关联专家技能和 MCP，输入需求描述”可作为阶段入口的候选交互方式，具体字段和行为留待产品阶段详细设计。

## 十、后续细化顺序

1. **产品阶段**：在已确认由产品专家执行的基础上，细化入口、上下文配置、产物预览、评审修订与实际效果验证。
2. **研发阶段**：评审需求澄清与多仓库设计流程，补充架构师约束、仓库规范模板及客户端输入/问题确认方式，再细化开发执行与提测。
3. **测试阶段**：用例规范、自动化范围、执行证据、缺陷与验收。
4. **统一机制**：编号、版本、产物引用、状态流转、审批及变更影响。
5. **外部集成**：再考虑 TAPD、钉钉、代码平台及其他连接器。

第一步先让三个阶段各自能够独立交付、被下一阶段理解和验证，再设计自动串联。本总览不直接触发任何阶段执行，后续以各阶段确认后的详细设计为准。
