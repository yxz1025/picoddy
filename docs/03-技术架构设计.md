# 03 · 技术架构设计

> 本篇是 PiCoddy-a 的**技术架构蓝图**，基于当前实际实现（Electron + IPC + Pi Agent + node:http）。
> **设计哲学：用 Electron 成熟生态 + Pi Agent 极简内核 + HTTP API 清晰边界——不做过度工程，但保留未来演进空间。**

---

## 一、设计哲学与架构总览

### 1.1 架构演进：从 Deno Desktop 到 Electron

项目早期选型为 Deno Desktop（见 [07-deno-desktop-spike验证](./07-deno-desktop-spike验证.md)），但在实际落地中发现 Deno Desktop 生态不成熟（全局热键缺失、打包复杂、平台兼容性问题），最终切换到 **Electron**。

**核心判断**：Electron 生态成熟稳定、跨平台支持完整、原生 API（Tray/Dock/GlobalShortcut）开箱即用。通过 preload + IPC（ipcMain.handle / ipcRenderer.invoke）实现主进程/渲染进程严格分离，API 调用 IPC 优先、HTTP 降级。

**核心特征**：
1. **Pi Agent 在 Electron 主进程 Node.js 22 runtime 直跑**——所有 provider SDK / 网络 / 文件零摩擦，无 CORS 限制。
2. **IPC 优先 + HTTP 降级**——前端通过 `client.ts` 正则路由表匹配 IPC 通道，未匹配自动降级 HTTP fetch。所有领域 CRUD 统一入口 `handleApi(req, path)`。
3. **Deno API 兼容层**——`src/shims/deno.ts` 在 Node.js 环境下提供 Deno API 模拟，实现 pi 代码零改动迁移。
4. **Domain-driven 设计**——业务能力按 domain 组织，每个 domain 提供 node/store 实现。
5. **Agent 工具系统**——Pi Agent 的 tool 直接调用能力模块的函数，同 runtime 零跨进程。

### 1.3 Electron 进程模型

```
Electron 主进程 (Node.js 22)              渲染进程 (Chromium)
┌─────────────────────────┐          ┌──────────────────────────┐
│ main.mjs                │          │ React App                │
│ ├─ BrowserWindow        │   IPC    │ ├─ window.electronAPI    │
│ ├─ ipcMain.handle()     │◄────────►│ ├─ client.ts (IPC优先)   │
│ ├─ handleApi()          │  HTTP    │ ├─ Sidebar/ChatArea      │
│ ├─ Pi Agent Engine      │◄────────►│ ├─ Composer              │
│ ├─ Domain Stores(SQLite)│ fallback │ ├─ ArtifactPanel         │
│ └─ Tray/Dock/Shortcut   │          │ └─ useStore (Zustand)    │
└─────────────────────────┘          └──────────────────────────┘
```

与原始 Deno Desktop 方案的关键差异：
- **通信方式**：Deno Desktop 用 in-process bindings，Electron 用 IPC + HTTP 双通道
- **前后端分离**：IPC 优先提供低延迟，HTTP 降级保证兼容性（浏览器也能调试 UI）
- **开发体验**：前端可用 Vite HMR 独立开发

## 三、核心数据流

### 3.1 启动流程

```
main.mjs
  ├─ 单实例锁 (app.requestSingleInstanceLock)
  ├─ 加载 Deno shim (src/shims/deno.ts)
  ├─ 注册 tsx/esbuild (TypeScript 实时编译)
  └─ app.whenReady()
       ├─ 1. initBackend()
       │    ├─ initDb() - SQLite 数据库初始化
       │    └─ import application.electron.ts - 装配所有模块
       ├─ 2. startServer() - Express HTTP 服务器
       ├─ 3. createWindow() - BrowserWindow
       ├─ 4. loadURL()
       │    ├─ 开发模式：http://localhost:5173 (Vite dev)
       │    └─ 生产模式：http://127.0.0.1:{port} (Express 静态服务)
       └─ 5. 平台功能
            ├─ Tray（macOS：菜单栏图标）
            ├─ GlobalShortcut（Alt+Space 全局热键）
            └─ Dock Menu（macOS）
```

### 3.2 一次对话的端到端路径

```
用户在前端输入"帮我把这周销售数据整理成周报"
  │
  │  IPC 优先调用 POST /api/prompt
  ▼
[Electron Main / node:http] → handleApi(req, "/api/prompt")
  │
  ├─► Agent 模块：agent.prompt(msg) → Pi Agent runAgentLoop
  │    │
  │    ├─► models.streamSimple() → DeepSeek/OpenAI API（流式）
  │    │    └─► SessionEventRelay 合并 delta → SSE → activeStream
  │    │
  │    ├─► Tool Call: read_doc{path}
  │    │    ├─► beforeToolCall → checkToolPermission → 放行/拦截
  │    │    ├─► execute → domains/doc/node/reader.ts (mammoth/exceljs)
  │    │    └─► afterToolCall → 审计日志
  │    │
  │    ├─► Tool Call: write_docx{sections}
  │    │    ├─► execute → domains/doc/node/writer.ts (docx)
  │    │    └─► 工件保存 → domains/artifact/node/store.ts
  │    │
  │    └─► Agent End → 返回完整结果
  │
  └─► message_end → 最终消息落库并一次性提交前端历史消息
```

### 3.3 前后端通信模式

```
前端 (React)                          后端 (Electron Main)
┌────────────────────┐               ┌────────────────────────┐
│ frontend/src/api/  │ IPC / HTTP    │ node:http + handleApi  │
│ client.ts          │──────────────►│                        │
│                    │◄──────────────│ 路由分发到各模块函数     │
│ Zustand Store      │    JSON       │                        │
│ useStore()         │               │ Agent / Domains / ...   │
└────────────────────┘               └────────────────────────┘
```

- 前端通过 `frontend/src/api/client.ts` 中的函数调用后端 API
- 后端 `application.electron.ts` 中的 `handleApi()` 函数统一处理所有 `/api/*` 路由
- 桌面 CRUD 调用以 IPC 为主、HTTP 为降级；Agent 流式事件通过本地 SSE + `ReadableStream` 传输
- 每会话仅有一个 `SessionEventRelay` 订阅 Provider；文本 delta 在后端约 32ms 合并
- 前端将当前回复放在独立 `activeStream`，约 50ms 合帧；`message_end` 后才提交历史消息和解析完整 Markdown
- 工具确认和用户提问由同一 SSE 实时推送，回答通过 HTTP/IPC 返回
- HTTP 层传递真实 AbortSignal，并在 `ServerResponse.write()` 背压时等待 `drain`

## 附：与原始 Deno Desktop 方案的对照

| 维度 | Deno Desktop 方案（已废弃） | **Electron 方案（当前）** |
|------|--------------------------|--------------------------|
| **桌面框架** | Deno Desktop 2.9 | Electron 43 |
| **进程模型** | 单 Deno runtime + webview | 主进程(Node.js) + 渲染进程(Chromium) |
| **前后端通信** | win.bind in-process channels | Express HTTP API |
| **Deno API** | 原生支持 | src/shims/deno.ts 兼容层 |
| **全局热键** | ❌ 不支持 | ✅ GlobalShortcut（Alt+Space） |
| **托盘** | Deno.Tray（实验性） | ✅ Tray（稳定） |
| **打包** | Deno 交叉编译 | ✅ electron-builder |
| **包体大小** | ~40MB（理论） | ~150MB+（Electron 基线） |
| **生态成熟度** | 实验阶段 | 生产级 |
| **跨平台** | 理论支持 | ✅ macOS + Windows + Linux |

选择 Electron 的核心原因：**成熟度优先**——Deno Desktop 在全局热键、进程管理、打包分发方面缺失关键能力，Electron 的生态成熟度能更快交付可用产品。
