## 2. 目标与非目标

目标：

1. 在研发设计右侧配置并查看本需求的部署自动化。
2. 复用 GitLab/Jenkins MCP，对明确的新代码版本执行构建、部署、就绪检查、自动化测试和报告归档。
3. 区分 Web、微前端、H5、小程序等目标，而非把所有前端当成一个 URL。
4. 用户一次启用明确范围后，符合条件的新版本自动执行；可暂停、追溯和恢复。
5. 未启用、缺配置或缺能力时，原有研发与产物交付照常工作。

非目标：生产发布、小程序提交审核/正式发布、自动合并 MR、强制推送、自动修改 Jenkins Job、首次引入全平台设备农场、自动修复业务代码、重做通用自动化调度器。本期不自动创建 Git 提交或推送未提交文件。

## 3. 方案选择

| 方式 | 优点 | 问题 |
| --- | --- | --- |
| 全靠 Agent 临时调用 MCP | 快速试用 | 难确保版本、去重、权限和中断恢复，聊天结束不等于交付完成 |
| 宿主维护执行记录，通过 MCP 调用固定能力（推荐） | 复用现有连接器，执行可追溯，恢复不依赖聊天历史 | 需要明确能力适配与流水线输入输出合同 |
| 新建独立 CI 服务并直接接 Jenkins/GitLab API | 可长期后台调度 | 扩大部署及凭据管理范围，当前无必要 |

采用第二种。Agent 提交“开发就绪候选”，宿主验证后派发；Jenkins 持续执行构建、部署、测试。不能只往提示词中加入“完成后发布”作为自动化实现。

## 4. 配置分层：仓库 → 交付目标 → 需求策略

### 4.1 仓库用途与交付类型分开

保留现有前端/后端/公共库等用途，在关联仓库编辑器中增加可选的“交付目标”。允许先关联仓库、稍后补充部署配置；阅读源码不要求配置 CI/CD。

一个仓库可有多个目标，例如 microapp 的多个子应用，或一个跨端项目生成 H5 和小程序。不能给仓库增加一个单选 `isMiniProgram` 就结束。分析范围与目标构建目录分别保存，不能把分析范围当成自动提交范围。

每个目标包含：

| 字段 | 说明 |
| --- | --- |
| 名称、目标 ID | 如营销后台、会员 H5、会员微信小程序 |
| 类型 | Web、微前端子应用、H5、小程序、后端服务、公共库/其他 |
| 仓库引用、相对构建目录 | 关联已有仓库；校验路径不能逃逸 |
| 平台子类型 | 小程序需明确微信/支付宝等；不能只识别框架名 |
| GitLab 连接器、项目 ID、分支 | 校验本地 origin 与远端项目一致；禁止只按名称猜测 |
| Jenkins 连接器、Job 标识 | 保存明确 Job 与参数映射，不让模型每次选择 |
| 环境标识、环境性质 | 仅测试/预览，独占或共享，标识用于全局环境锁 |
| 触发方式 | MCP 显式触发，或已有 Git 推送触发，两者二选一 |
| 就绪检查与版本证明 | Web 地址/版本标记，或平台产物与 runner 合同 |
| 测试配置引用 | 已有测试套件、runner、数据配置和报告位置 |

凭据仅保留现有连接器或 Jenkins 凭据引用，不复制到目标 JSON、提示词、截图或报告。账号/AppID 可为目标配置，私钥和登录态不能作为普通资产交付。

一期配置作用域为当前需求，避免无意建立新的全局配置事实源；未来的项目模板复用另行设计。

### 4.2 需求级自动化策略

勾选“本需求开发就绪后自动部署测试”，默认关闭。首次启用在同一面板展示并保存授权摘要：目标集合、分支、测试环境、Jenkins Job、测试套件、触发方式、有效期和操作者。

授权覆盖所选分支后续符合条件的新提交；不授权任意仓库、生产发布、MR 合并、Git 提交/推送和修改流水线。Git 提交推送仍按已有明确授权进行；尚未推送时显示“等待代码提交并推送”，不会构建远端旧版本。

部署和自动测试分开选择。默认目标为“部署并测试”；缺少 runner 时不能静默降级，用户可显式选择“仅部署”，结果始终标记测试未执行。

需求归档、用户关闭、授权到期停止后续派发。更换项目、分支、环境、Job、连接器身份或扩大测试操作范围后，策略转为待重新确认。普通代码 SHA 更新不要求再次确认。

## 5. 右侧入口与交互

研发设计右侧增加“部署与测试”页签，其他阶段结构保持不变。测试阶段可以通过资产/运行引用查看结果，不因此自动跳转阶段。

```text
代码仓库 | 资产 | 需求 | 任务 | 部署与测试

部署与测试
[ ] 本需求开发就绪后自动部署测试

交付目标：营销后台 · 微前端
分支：需求分支     环境：共享测试
流水线：已绑定 Jenkins Job
执行范围：部署并执行已选测试
授权范围与有效期：……

[配置目标] [校验连接与配置] [部署测试一次]

最近运行：提交 abc1234
代码就绪 → 排队 → 构建 → 部署 → 就绪检查 → 测试 → 报告
构建链接 / 环境入口 / 测试统计 / 阻塞原因

```

“校验连接与配置”只调用只读能力，不用真实构建作为连通性探测。“部署测试一次”展示并绑定当前版本，只授权这一次，不自动开启长期策略。

关闭自动触发不等于撤销已发出的远端构建。取消远端运行是独立操作，仅在 MCP 和流水线能可靠取消时提供；已部署不会自动回滚。修复失败项暂由用户在已有研发会话中明确安排。

## 6. 开发就绪与自动触发

不监听每次文件保存，不用会话从 busy 变 idle、模型回复“已完成”、产物上传成功或 TAPD 状态变化直接触发部署。

新增结构化 `development_ready` 候选，由当前需求的开发任务在结束时提交，包含需求/会话 ID、输入基线版本、仓库和目标、代码 SHA、变更摘要、实际检查证据。它是待校验声明，不能自行提升权限。

宿主校验后才创建运行：

1. 当前策略开启、未到期，候选来源属于本需求且不是仅讨论。
2. 目标、分支、环境、Job 和工具合同与授权版本一致。
3. 候选与当前确认的需求基线一致，约定的检查确已执行且通过；未执行不能算通过。
4. 一期要求目标仓库工作区干净，完整 SHA 已推送，GitLab 核验远端指定分支 HEAD 与该 SHA 一致。其他未提交修改必须由用户处理，不自动提交或丢弃。
5. 新 SHA 相对上次交付确实影响目标或其声明的共享依赖；依赖影响不确定时标记待判断，不静默排除。允许显式执行同版本重测，但属于新的运行尝试。
6. 若项目配置要求先代码审核，校验绑定该 SHA 的审核记录；不能把勾选部署解释为绕过既有审核。
7. 所需能力、环境互斥和测试前置条件满足。

同一代码版本、目标和配置版本只自动运行一次。后续代码变更完成并重新提交候选时产生新运行。这里的“每次完成”是通过校验的一次开发交付，不是每条聊天消息。

GitLab MCP 用于远端项目、分支、提交和必要审核证据查询；本地提交/推送属于已有 Git 执行链，不强行经 GitLab 文件 API 重写工作区内容。

## 7. MCP 与 Jenkins 的执行合同

配置时按需连接用户选定的 MCP，读取真实工具 Schema，以具体适配器映射到以下语义能力；不假设工具必定具有某个名字，不根据工具描述由模型在运行时任意选择写工具。

| 系统 | 必需能力 | 缺失时行为 |
| --- | --- | --- |
| GitLab | 查询项目、分支完整 SHA，按策略查询审核证据 | 阻塞代码核验 |
| Jenkins | 查询 Job/参数，按运行标识与 SHA 找到对应队列或构建 | 禁止启用无人值守运行 |
| Jenkins（显式触发模式） | 触发允许的参数化 Job，获取或反查队列回执 | 不发送构建 |
| Jenkins | 查询排队/构建/部署/测试状态，读取结果及报告 | 缺少环节不能标记成功 |
| Jenkins（可选） | 取消指定排队或构建 | 无此能力隐藏远端取消按钮 |

所有调用经过当前连接器运行时及权限边界，只允许本运行绑定的工具和参数。工作流授权是一条显式的任务作用域，不把连接器全局注入，也不让后续普通聊天继承权限。工具 Schema、连接器账号/来源发生变化时重新校验。

流水线接受不可变代码 SHA、目标 ID、测试环境及客户端 runId（通过配置映射到真实参数名），实际 checkout 该 SHA，回传实际构建 SHA。只接受分支名且无法锁定或证明版本的 Job 不满足自动部署条件。

默认由同一个 Jenkins 流水线完成构建、部署、环境就绪和测试，使桌面端退出后已派发的链路仍能继续。若现有 Job 只构建，则先明确补齐流水线合同；不能把 SUCCESS 当成部署完成。修改 Jenkinsfile/Job 本身是后续单独确认的工作。

已经由推送自动触发 Jenkins 的项目采用观察模式，匹配已存在的构建，不再同时 MCP 触发。已有自动触发若早于开发就绪，界面明确这是外部流水线触发，不能声称由本需求勾选控制；测试部署仍需流水线侧门禁。

## 8. 不同交付类型的完成条件

| 类型 | 部署/交付就绪条件 | 自动化执行与证据 |
| --- | --- | --- |
| Web | 指定 URL 就绪，版本标记与 SHA 一致 | 已配置浏览器 runner，页面/接口断言、截图、Trace/报告 |
| 微前端 | 子应用产物及宿主入口就绪，版本匹配 | 子应用检查加宿主路由、登录、权限及集成回归 |
| H5 | 指定地址及目标容器可访问 | 浏览器视口测试与真实容器测试分开报告，不把模拟视口当真机 |
| 小程序 | 明确平台、AppID、开发/体验版本，产物与 SHA 可追溯 | 对应平台 runner；开发者工具与真机结果分别标记 |
| 后端 | 健康及版本检查、依赖就绪 | 已配置 API/集成测试 |
| 公共库/其他 | 对应构建或制品可追溯 | 构建/消费方验证；不默认发布包或执行页面 E2E |

小程序二维码或体验包生成只代表可供测试，不代表测试通过。没有平台 runner、设备、登录态或权限时展示具体阻塞，并可在用户明确选择“仅交付体验版本”后结束部署部分；不冒充完整自动化。

一期先交付 Web/微前端实际链路，小程序配置和状态识别一并设计；接入具体小程序平台执行器作为后续子任务。不能在未核验其 MCP/流水线能力前承诺全平台无人值守。

## 9. 运行状态、并发与恢复

状态：`validating → queued → building → deploying → checking → testing → succeeded`。另有 `blocked / failed / unknown / cancelled / superseded`，保留失败发生的环节。部署成功与测试结果分别保存，“仅部署”不会产生测试通过。

- SQLite 先记录运行意图及唯一键，再请求远端。唯一键包括需求、目标、完整 SHA、配置版本和测试版本；人工重跑有独立 attempt。
- 每次提交保存 runId、队列 ID、构建编号/URL、实际 SHA、产物与报告引用、状态时间戳、授权版本和脱敏错误。
- 写请求超时视为结果未知，通过 runId/队列回执反查；无法证明未受理时不自动再次触发。要求流水线能关联 runId，不能承诺 MCP 天然具备幂等性。
- 共享环境需要 Jenkins/部署服务提供跨客户端、跨 Job 的环境锁，覆盖部署到测试结束。单机 SQLite 锁或单 Job 禁止并发都不足以防止其他 Job 覆盖环境。无远端互斥时禁止共享环境无人值守部署。
- 新版本等待同目标现有运行结束；尚未派发的旧候选可标记 superseded。默认不强行终止正在部署的任务。
- 测试开始与结束核验部署版本，发现环境被外部替换则结果无效，不能归因成代码失败或通过。
- 一期各目标独立串行运行、分别报告；不承诺跨仓库原子发布。有严格前后端部署依赖时，绑定能接收版本清单的组合流水线，否则阻塞该组合自动化。
- 主进程在用户开启策略或打开面板后按需跟踪，离开面板但应用存活可以继续。应用退出后由已派发 Jenkins 流水线执行；再次打开面板读取持久记录并对账，不新增启动时联网或全局调度入口。
- 退出期间未派发的本地候选不会自行执行；恢复后重新校验授权、代码和环境，再派发，失效候选不重放。
- 授权过期、MCP 不可达、测试账号失效属于阻塞；不循环弹授权、不自动修改业务代码。

## 10. 数据与模块边界

拟新增需求领域的交付目标、自动化策略、运行记录及运行事件数据，均按账号和需求空间校验归属。配置变化产生新版本，运行引用不可变配置快照。使用现有 DB 与资产能力，避免把聊天文本作为状态事实源。

建议职责：

- `deployment_targets`：目标配置与校验。
- `deployment_policy`：启停、授权范围及版本。
- `deployment_runs`：状态、去重、对账和证据引用。
- `deployment_mcp`：已核验工具的固定适配与响应校验。
- `DeploymentAutomationPanel`：配置、授权摘要、运行进度与报告入口。

以上是拟新增模块职责，实施时按现有目录约定落位，不提前创建空代码。

新增 API 包括目标 CRUD、只读校验、策略启停、就绪候选提交、单次运行、运行列表/详情/对账和可用的取消能力；同步前端映射、preload 白名单、IPC handler、统一业务 API。敏感写操作必须遵循既有可信调用和权限检查，不新增匿名本地 HTTP 部署入口。

结果文件通过现有资产服务显式登记来源、版本及内容哈希，不放宽会话目录校验。大体积 Trace/视频优先保留受控 Jenkins 报告引用，处理保留期限和失效状态；日志脱敏。TAPD 用例上传、资产提交、阶段完成仍是原来的独立操作，本期不自动回写测试执行结果到 TAPD。

## 11. 影响范围与风险

预计修改仓库关联编辑器、研发设计右侧面板、需求领域服务、API/IPC 映射，以及开发就绪候选的工具/上下文接入。复用 MCP 运行时，尽量不修改连接建立和会话生命周期。

不修改 `main.mjs` 启动逻辑，不启动全量 MCP，不恢复旧开发阶段，不改变现有阶段键、文件收集、普通测试产物上传和 TAPD 流转条件。现有会话只增加可选的就绪候选提交能力，未启用策略时不触发外部动作。

风险重点：MCP 能力不全、分支漂移、共享环境覆盖、未知请求重复触发、小程序 runner 不具备、把模拟测试当真实联调、工作区已有修改被误提交。分别通过配置校验、SHA 锁定、远端锁、对账、明确阻塞、证据分级和不自动提交推送控制。

所有本地路径处理使用 Node 跨平台 API、进程执行使用参数数组；不引入 Bash 命令拼接或系统 PATH 依赖。客户端能力需验证 macOS/Windows；Jenkins 执行节点平台由目标合同明确，不要求所有远端节点使用同一系统。

## 12. 验证与交付顺序

第一步：只读核验真实 MCP Schema 和一个试点 Jenkins Job，确认版本参数、回执、状态、环境锁和报告合同；不触发构建。

第二步：实现目标配置、策略、结构化就绪事件和持久运行记录，打通一个 Web/微前端流水线。验证仅部署与部署加测试两种结果。

第三步：接入具体小程序平台执行器以及其体验版本/设备合同。自动修复、多仓库编排、项目模板共享另行设计，不混入首期。

需要维护的验证场景：

1. 未开启策略、仅讨论、无新 SHA、检查未执行时零远端写入。
2. 每次文件保存和会话结束都不直接触发；合法候选只触发一次。
3. 未推送、分支不符、远端 SHA 改变、基线失效时明确阻塞。
4. 写请求已受理但响应丢失，重启后对账得到原构建，不重复发布。
5. 关闭策略阻止新派发，已发起构建状态仍可查看。
6. 多客户端/多 Job 共享环境串行，版本被替换时不误报测试通过。
7. Jenkins SUCCESS 但部署未就绪、零用例/全部跳过、报告缺失，都不标记端到端通过。
8. 小程序仅二维码、没有 runner 时显示待验证。
9. 普通会话不继承工作流 MCP 权限；连接器更换后旧策略不能继续写。
10. 历史阶段会话、现有资产交付、TAPD 用例上传和启动行为保持原样。

遵循项目约束：设计阶段只检查文档差异；实现后默认仅语法、类型和差异检查。测试套件、真实 Git 推送、Jenkins 构建/部署及 Windows 构建启动验证，在对应明确授权下执行并分别报告，不能以模拟结果替代。

## 13. 参考与结论边界

- Jenkins [Remote Access API](https://www.jenkins.io/doc/book/using/remote-access-api/)：提供构建触发与远端查询基础；不证明当前 MCP 已封装这些能力。
- Jenkins [Pipeline Syntax](https://www.jenkins.io/doc/book/pipeline/syntax/)：说明单流水线并发控制；共享环境跨 Job 互斥需另行核验。
- 项目源码与已确认设计：`2026-09-18-requirement-development-design-stages-design.md`、`docs/19-MCP连接器统一架构设计.md`、`docs/12-MCP按需连接与会话工具隔离处理记忆.md`。

本方案推荐：研发设计右侧放“部署与测试”，关联仓库下配置多个交付目标，按需求启用有范围的自动化授权；复用 MCP 调用能力，由宿主持久化状态、Jenkins 执行实际流水线。用户已确认入口位置，其余方案等待评审。

## 14. 实施前核验与补充方案（2026-09-23）

用户已确认上述主体方案。实际读取本机 MCP 配置时只输出连接器名称、包路径及环境变量键名，未输出凭据值；未启动 MCP 或调用远端写操作。

已安装包源码核验结果：

| 对象 | 已有能力 | 自动化所缺信息 |
| --- | --- | --- |
| `@masuratech/gitlab-mcp-server` 1.0.0 | `get_project`、`list_branches`、文件读取等 | `list_branches` 将 commit 映射为 `short_id`，未提供精确分支完整 SHA 查询工具 |
| `@kud/mcp-jenkins` 2.3.0 | 参数化触发、队列列表、构建状态、制品、测试报告 | `normalizeBuild` 只保留 id/result/durationMs/timestamp/url；不返回 parameters、queueId、实际 checkout SHA；队列列表也不返回 parameters 或 executable |

源码证据位于已安装包的 `dist/index.js`（GitLab）、`dist/tool-manifest.js` 和 `dist/lib/jenkins-client.js`（Jenkins）。这证明包的封装合同有限，不代表 Jenkins/GitLab 官方 API 没有这些能力，也不代表用户的服务连接失败。

因此不能把“最新构建”或相同短 SHA 当成可靠关联，不能在触发响应丢失后安全重发。缺口发生在主体方案第一步的能力准入检查，尚未进入生产代码实现。

### 14.1 推荐补充：受控扩展 MCP 的只读合同

保留已配置的连接器名称、凭据来源及现有写工具，在仓库内维护可审查、可打包、版本固定的扩展实现，不直接修改用户目录或 node_modules 中的第三方安装文件。

至少补充以下语义接口，实际命名由扩展实现固定：

1. GitLab 精确分支查询：输入项目 ID、分支，输出完整 commit ID 和项目身份。
2. Jenkins 精确队列查询：输入 queueId，输出取消状态、参数与 executable build ID。
3. Jenkins 按 runId 查队列/构建：限定 Job、参数名和值，支持有界分页和明确的检索范围；未查到不等于未受理。
4. Jenkins 构建详情：输出队列 ID、非秘密关联参数和 SCM revision；流水线实际部署 SHA 仍需可信产物报告，不用请求参数冒充。

只读扩展必须复用明确的现有服务地址与凭据引用、采用超时和响应校验，并将读取字段限制在运行核验所需范围。Jenkins 触发仍经过已绑定 MCP 写能力，不增加任意 HTTP 请求工具。连接器安装/升级与扩展加载的具体实现须先核查现有受管包方式，不改变应用启动顺序。

这会扩大原方案的连接器实现范围，因此需要确认此补充后再实施，而不是默默替换用户已有 MCP。

### 14.2 备选方案

- 宿主直接使用 GitLab/Jenkins 官方只读 API 补齐查询，写操作仍走 MCP：实现可能更小，但形成 MCP 与 API 双通道，需明确凭据与错误处理边界，偏离原来统一 MCP 路径。
- 保持当前 MCP 不变：仅支持人工触发和人工确认版本，不能交付已确认的可靠自动部署与中断对账目标，不推荐。

后续配置仍需用户选择实际 Job、测试环境和分支，这些属于功能启用时配置，不要求本次把生产或测试凭据写入设计文档。
