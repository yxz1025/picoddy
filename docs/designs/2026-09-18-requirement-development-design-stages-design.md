# 需求阶段简化与研发设计命名

## 背景与现状

用户要求项目需求中的“架构设计”改为“研发设计”，继续关联软件架构师，移除之后的“研发计划”和“软件开发”阶段。目前前端阶段数组、状态映射、专家映射、后端阶段名称及资产范围共同依赖数字阶段编号。直接删除数组元素会改变测试阶段等编号并误读历史资产。

## 目标与非目标

当前可进入阶段为：设计分析、产品 PRD、设计评审、研发设计、代码审核、自动测试、构建验证、交付归档。研发设计继续自动召唤 teach-engineer/software-architect。其他专家和测试生成/明确发布流程保持现有规则。不删除历史会话、资产或同步回执，不实施代码开发。

## 方案

采用稳定阶段 ID 与有序可用阶段清单，不将显示位置用作持久化编号。保留仍存在阶段的原数字 ID，移除计划、开发的可用入口；阶段选择、流程推进、状态映射和专家路由均使用同一有效阶段集合。界面显示序号按有效阶段顺序计算。

“架构设计”显示名称改为“研发设计”；内部既有阶段会话键保持稳定，不因显示命名重复创建会话或丢失资产引用。待排期、已排期、开发计划等状态统一进入研发设计；开发中与开发完成继续进入测试专家阶段。重新打开映射到研发设计，不再进入被移除的软件开发阶段。

同步更新后端输入/交付阶段查找和前端说明、模拟推进逻辑，避免删掉入口后留下不可到达的阶段或专家。历史产物保留在原需求中供引用。

历史会话的资产收集允许解析已归档阶段编号，当前输入选择仍拒绝已移除阶段；避免资产列表遍历旧会话时中断整个需求的读取。

## 影响范围

projectDemo 阶段定义、ProjectPanel、RequirementChat、状态与专家映射、仓库关联文案、后端阶段定义/上下文/交付及相关测试源码和专项文档。

## 风险与验证

主要风险是编号错位、历史会话重新创建和下游资产不可引用。保留稳定标识、显式顺序并维护回归测试源码约束。按项目要求仅执行 TypeScript、语法和差异检查，不自动运行测试或构建；使用现有跨平台路径和接口。
