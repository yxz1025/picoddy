# 云端接入桌面同源企业登录

状态：用户已确认，代码与本地服务接入完成；真实企业账号换票回调等待用户本人登录验收。

## 背景与现状

用户要求云端使用桌面相同的登录体系，而非另建邮箱密码账号。桌面实际入口为 `src/auth/cas.ts`、`application.electron.ts`：跳转企业 CAS，回调后调用 PICODDY 网关 `sys/cas/client/validateLogin`，取得用户资料及 accessToken。历史 CAS 设计中的直接 serviceValidate 并非当前实际登录路径。

云端目前使用邮箱密码、PostgreSQL users/sessions 和 HttpOnly Cookie。资源、空间、技能、任务和 OSS 路径通过云端 owner UUID 隔离。刚启动的是独立云端数据库，上次检查账号列表为空；实施前须重新检查，不据此推断所有表永远为空。

## 目标与非目标

- 同一个企业认证入口、同源用户身份；前端恢复桌面登录页的样式和“使用企业账号登录”按钮。
- 首次企业认证成功自动创建云端用户，无额外注册、密码或管理员建号步骤。
- 模型仍由每位用户登录后自行配置，不注入统一模型或桌面配置。
- 云端数据库、技能、会话和 OSS 数据保持独立，桌面目录完全不改动。
- 本轮不做全公司单点登出、CAS 服务端修改、桌面数据迁移或自动授予管理员权限。

## 方案比较

1. **推荐：桌面同源企业认证 + 云端独立会话。** 复用协议及网关字段，按浏览器完成认证，内部继续使用云端 owner UUID，改动集中在认证与登录 UI。
2. 直接共享桌面登录态：依赖本机且与浏览器多人隔离冲突，不采用。
3. 保留邮箱密码并添加第二入口：需要维护双重账号绑定和密码入口，不符合本次统一登录与不保留旧逻辑的要求，不采用。

## 登录流程

1. Web 请求当前会话，未登录只显示企业登录页。
2. 同源 POST 登录请求生成随机 state 和浏览器绑定秘密；仅返回受信任企业登录地址，浏览器当前页跳转。服务端不调用 Electron 或打开浏览器。
3. 将 challenge（秘密摘要、state 摘要、完整 service URL、到期时间）保存在 PostgreSQL，TTL 10 分钟；绑定 HttpOnly、SameSite=Lax Cookie，生产使用 Secure。不同浏览器互不覆盖；同浏览器重新发起登录使旧请求失效。
4. 回调必须同时校验 Cookie、state、期限，并原子消费 challenge。service 基于配置 PUBLIC_ORIGIN 构造并保存，换票时逐字使用原地址，不信任 Host 或任意 returnUrl。
5. 后端只调用一次与桌面相同的 PICODDY 换票接口；不先调用 serviceValidate 消耗 ticket。请求有超时、响应大小限制、禁止重定向及严格响应结构校验。
6. 以固定身份提供方及网关稳定主体标识唯一映射云端用户。沿用桌面网关 username 主体，资料缺少该标识时明确失败，不用邮箱/姓名自动合并身份。仅保留身份与展示必需字段，不存无消费者的原始完整资料；需在真实回调确认字段契约。
7. 并发首次登录通过唯一约束/upsert 取得同一 owner UUID，更新安全白名单资料；禁用用户拒绝登录，不自动解除禁用。所有新用户默认普通用户。
8. 生成新的随机云端会话令牌，数据库仅存摘要；网关 accessToken 使用 ENCRYPTION_KEY 加密并绑定当前云端会话，供后端按身份访问企业能力。不得给浏览器、模型上下文或沙箱直接下发登录令牌。
9. 成功回调用 303 返回固定首页，移除地址栏 ticket/state；失败也转回固定登录页的安全错误码。认证响应设置 no-store、no-referrer，不记录 ticket、完整回调地址或令牌。

## 会话与企业令牌边界

保留现有云端 HttpOnly 会话、业务接口鉴权和写请求 Origin 校验。页面需要的昵称、头像等采用白名单 DTO，不返回网关原始完整资料或 token。

退出仅撤销当前云端会话及其企业凭据、清理该会话的企业连接缓存，不退出桌面或公司其他系统；过期/无效网关令牌要求重新企业认证，无文档支持时不虚构自动刷新。不同用户或会话的凭据不得存到进程全局变量。企业调用入口在实施中逐一确认并接入明确的 owner/session 上下文，不能将“登录成功”等同所有企业扩展已验收。

## 数据结构与影响范围

- 仅修改 cloud/：认证模块、HTTP 路由、配置、schema、管理员命令、登录组件/状态管理/API 适配、测试与运维文档。
- users 增加固定提供方及主体唯一约束、昵称/头像/必要资料；email 可空，只作联系资料。移除 password_hash 及密码登录专用逻辑，管理员工具只保留用户查询/禁用/角色管理等必要功能。
- 新增登录 challenge 表；sessions 增加加密企业凭据。资源 owner UUID 与现有租户查询/OSS key 规则不变。
- 不写历史迁移、不清空现有数据库。实施时为新 schema 创建明确命名的独立空开发库并切换 cloud/.env，保留当前 picoddy_cloud 数据库；生产也是空库初始化。
- 默认登录/换票地址与桌面源码一致；允许通过服务端明确配置覆盖，要求受信任 HTTPS endpoint。PUBLIC_ORIGIN 本地为 http://localhost:8080，部署为实际 HTTPS 域名。

## 风险及外部前置

- CAS 是否允许本地或部署域名的 service 回调须真实验证；若未登记，需要企业 SSO 管理员配置，不能靠改代码绕过。
- 浏览器需能访问 CAS，云端后端需能访问 PICODDY 网关。仅做只读连通性检查不能证明换票成功，真实登录须用户本人完成。
- 身份主体字段稳定性、账号禁用和令牌有效期需核验；不得以昵称、邮箱或客户端提交的 ID 授权。
- 新 schema 使用新空库，已有运行服务需有序重启；不删除当前数据库、持久卷或 OSS 数据。
- Windows 浏览器沿用标准跳转和 Cookie；Node 代码不用 POSIX/Electron API。未经 Windows 实机验证不声称跨平台已验收。

## 验证与验收

经授权执行认证单元/集成测试：state 伪造、浏览器错配、过期、回放、并发首次登录、网关错误/超时/超大响应、禁用账号、Cookie 属性、Origin 防护、退出撤销、身份唯一映射和用户越权。使用明确专用测试库，不清理业务数据库。

类型检查、构建及浏览器验证：登录样式与桌面一致、无邮箱密码框、错误后可重试、成功跳转首页、刷新保留会话、设置里自行配置模型。

真实验收：用户在浏览器完成企业认证，后端实际换票、形成云端独立会话、退出后访问被拒绝；验证过程中不采集密码或在日志输出 ticket/token。第二账号隔离验收需第二个授权企业账号，不能用 mock 冒充。

## 已确认决策

采用方案 1；移除云端邮箱密码入口；企业认证后自动建立普通用户；新建空库承载新 schema 并保留当前数据库。
