# 项目规范发现与产物路径解析

设计、开发和初始化时共同使用本规则。项目已确认规范和例外优先于适用的公司规范，公司规范优先于通用参考。代码提供当前事实，PRD 提供目标行为；二者不是可以简单覆盖的优先级关系，冲突须由相应负责人确认。

## 找到入口

1. 读取目标仓库及当前模块适用的 AGENTS.md、CLAUDE.md 等规则，沿 README.md、docs/README.md 和既有文档索引找到规范入口。
2. 无明确索引时，在仓库内查找 design-guidelines.md 或其他实际命名的开发规范，读取候选内容、范围、状态和引用，不能仅依赖目录名。
3. 多个入口按仓库/模块适用范围组合；同一范围互相冲突时列明证据和待确认事项，不能任取一份或合并冲突规则。
4. 根据入口读取相关架构、设计、计划、接口和测试资料。未索引文档可能是历史草案或旧方案，不自动提升为当前约束。

## 输出路径映射

规范应记录每种产物的目录、命名、权威入口、适用模块和版本状态。已确认映射优先；没有映射时，根据实际目录内容提出补齐方案，缺失类型单独确定位置，不以其中一种缺失为由重建全部目录。

例如仓库确认 designs 存设计、plans 存任务时，生成 `docs/designs/<需求编号>-<repo-id>-design.md` 与 `docs/plans/<需求编号>-<repo-id>-tasks.md`。没有已有约定时，才默认 `docs/requirements/<需求编号>/`。questions、coordination、review 等同样按已确认映射定位。

需求编号与 repo-id 仍必须在文件名、元信息及文档引用中一致。仅当路径包含需求编号目录时才检查该目录一致性；按类型归档不强制再增加需求子目录。

## 初始化后的可发现性

生成或刷新规范时，在现有仓库规则或 docs/README.md 索引中增量登记规范入口的相对链接、适用范围和状态。优先 docs 索引，避免复制整套规则。写入须在已授权文档范围内；没有索引时可创建 docs/README.md。若入口登记不在授权范围，交付准确位置和待登记说明，不能声称其他专家已能自动加载。

已授权生成草案可以直接写入并标记 draft，写入授权和规范审批分开。没有真实确认不能标 approved。读取这些入口是本专家的执行约定；其他工具或专家是否自动读取取决于其入口规则，不能由文档自身保证。

## 按仓库与模块选择技术参考

逐仓库识别构建文件、依赖、源码、启动入口和测试；package.json 可能只用于前端或构建，不能据此断定 Node.js 后端。Java 构建文件也不等于使用 Spring/MyBatis。

多仓库分别选择适用参考；混合仓库按模块划分，允许多个适配器在各自范围使用。同一需求不限制只能有一个适配器。纯前端优先项目组件、路由和状态管理规范，没有匹配适配器时直接依据项目资料工作，不强行选最接近的后端框架。

公司 Java 项目使用公司 Java 规范，并核实仓库例外、模块名称、版本和实际启用能力。公司范围可由用户说明或项目材料确认；外部项目不自动继承公司规则，适用范围未知且影响设计时再澄清。
