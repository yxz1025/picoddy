# 任务人工评估与授权开发

适用于依据本专家研发设计产物进行任务评估、调整和开发。独立代码咨询不强制生成整套文档；但不得借切换模式绕过已有需求任务的评估门槛。

## 1. tasks 是草案，不是执行授权

设计完成后生成的任务评审状态为“草案/待评估”，执行状态为“未开始”。交付评估材料后等待人的意见，不立即编写业务代码。

人工评估内容：任务范围与粒度、需求覆盖、仓库归属、依赖顺序、技术可行性、工作量、负责人、排期、完成标准和验证方式。工作量允许专家给建议及估算依据，不编造团队产能、人员承诺或确定交期；人员与排期待确认时明确标记。

实际意见记录到同需求的 review，引用任务 ID 及任务版本。用户笼统说“继续完善”只授权完善当前材料，不等于确认全部任务或开始代码开发。

## 2. 两类状态独立维护

| 维度 | 状态 |
| --- | --- |
| 评审状态 | 草案 → 待评估 → 待调整 → 已确认；调整后可再次待评估，无修改可直接确认 |
| 执行状态 | 未开始 → 进行中 → 阻塞 / 待验证 → 已完成 |

开发授权另行记录，不用评审状态代替。记录实际授权来源、明确任务 ID/范围和所针对的版本；同一条明确消息可以同时确认版本与授权执行，但两项含义都必须明确，不能从“设计可以”推断“马上开发”。

专家可以整理实际人工确认的记录，不能自行制造“人工已确认”。未确认的任务不可执行。已确认但未授权的任务保持未开始，交付后等待明确开发请求。

## 3. 依据意见修订并确认基线

- 调整说明逐项关联任务 ID、原意见、改动和影响。
- 只变更任务拆分/顺序时更新 tasks；影响方案时同步 design，影响系统行为时同步 spec，涉及产品含义时返回产品补充流程。
- 修改范围、方案、关键依赖或完成标准后，将受影响任务重新置为待评估，暂停其执行；不必重审无关且独立的已确认任务。
- 保留稳定任务 ID。拆分时原任务注明不再执行及后继 ID，合并时保留映射，不复用废弃 ID 或将取消任务标成已完成。
- 保留旧版意见和执行记录，当前状态须匹配新版，不能继承失效审批。

确认基线至少包括任务文档版本及可核验引用、所确认任务集合、产品/spec/design/契约版本、确认人的实际身份或来源和未决项。不要求为了确认自动提交 Git；未提交文件可记录已确认快照的内容哈希并保留对应内容，不能只凭可随时变化的文件名识别版本。

## 4. 执行前检查

先按 [研发产物自动校验](artifact-validation.md) 对当前任务及关联产物运行只读校验，重点核对引用版本、快照与依赖。错误先处理，未验证项说明阶段影响；校验结果不代替以下人工确认和实际代码检查。

按 [项目规范发现与路径解析](repository-context-routing.md) 定位当前仓库的规范和产物；tasks 可以位于已登记的 docs/plans 等目录，不固定从 docs/requirements 读取。

用户明确授权后，先读取 tasks、关联 spec/design、PRD 验收、问题闭环记录及仓库规范，确认：

1. 选中的任务已获人工确认，且授权覆盖当前版本及仓库。
2. 关键需求问题已关闭；依赖任务、接口契约和环境确实满足条件。
3. 当前代码与设计基准的差异已检查；识别已完成/部分实现内容，避免重复开发。
4. 本地未提交改动已识别并保留，冲突时暂停受影响部分询问。
5. 使用项目实际构建、测试入口和支持平台，不照抄示例命令。

不能只相信 tasks 中“依赖已完成”就跳过实际契约核对。任务未经评估、版本已变或代码差异会改变方案时，先返回评估/澄清，不因为用户说“按 tasks 开发”就伪造批准历史。

## 5. 按任务实施

按依赖顺序处理已确认且获授权的任务；独立任务可在安全范围内并行，不擅自扩大到其他仓库或未授权任务。每项记录需求/验收编号、实际改动和验证。

遵循当前仓库实现、组件/接口契约和项目规范，做范围内的代码及测试增量。发现设计不成立、业务不清或需要改变共享接口时，先给出证据和调整建议，暂停受影响任务；不顺手重构、不自行改产品规则。

实现过程允许项目正常且已授权的检查。安装依赖、切分支、提交、推送、建 PR、数据库变更或部署等操作须符合用户授权和运行环境权限，不能从“开始开发”推断无限外部写权限。禁止技能时直接依据项目和本专家文档实施，不调用 fullstack-dev。

## 6. 验证与完成

对照已确认完成标准执行适用的构建、类型检查、单元/集成/端到端测试或人工检查，记录实际命令、平台、结果、代码状态和证据。项目支持多个平台时，缺少相应环境就明确说明未验证；不能将本机通过推断成全部平台通过。

- 代码写完但检查未跑：待验证，不是已完成。
- 验证失败或环境/依赖阻塞：记录失败和影响，保持待验证或阻塞。
- 人工代码评审是约定完成条件时：等待实际评审结论，不能用 AI 自检替代。
- 只有已约定完成标准及必要验证/评审满足后，才能更新已完成。
- 有权人员明确调整完成标准或接受例外时记录决定和残余风险，不把未验证项写成通过。

最终报告按任务列实际状态，不以一个仓库完成代表整个需求完成。中断续跑时重新核对代码、任务版本和证据，不重复已验证工作或覆盖用户变更。

## 7. 执行记录与提测

在 tasks 中维护执行状态和简要证据；详细验证及代码评审记录可引用已有系统或同需求 review，避免重复状态源。

按仓库生成 `<需求编号>-<repo-id>-handoff.md`，包含：

- 需求、产品、设计和任务基线，实际完成/未完成任务。
- 代码提交或明确的未提交工作区状态；真实制品版本（若已有）。
- 文件/模块变化、测试环境和数据准备、实际验证结果。
- 已知缺陷、未验证项、风险、回归范围及代码评审情况。
- 跨仓库依赖版本和整体验证状态。

未具备提测条件只能交付进展记录或提测草案。牵头仓库协调真实版本组合，未提交且无可定位制品时不能声称正式可提测。代码开发完成不等于测试阶段验收通过，更不等于发布授权。
