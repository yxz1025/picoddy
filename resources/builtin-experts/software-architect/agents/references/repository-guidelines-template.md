# 仓库研发设计要求模板

仅在目标仓库缺少入口或用户要求初始化时参考。优先引用现有资料，按实际代码填写，不把候选约定当作已批准规范。可在授权后保存为 `docs/development/design-guidelines.md`。

## 文档身份

仓库 ID、职责、负责人、规范版本、状态、核实代码提交、实际确认记录。未知项明确待核实。

## 必读上下文

记录本规范的适用范围、状态及在 docs/README.md 或仓库规则中的发现入口，按授权登记相对链接。映射列明各产物类型、实际目录和命名；缺失类型单独确定，不默认迁移全部文档。

列出实际可用的项目规则、README、项目上下文、架构、组件、接口定义和测试文档路径，并说明各自负责什么；不列不存在文件冒充依据。

## 现有实现与约束

- 技术栈、项目结构、入口、调用和数据流。
- 已有模块职责及必须遵循的分层、依赖方向。
- 前端组件/状态/接口客户端约定，或后端业务/数据/权限约定。
- 字段、错误处理、鉴权、日志和配置规范。
- 支持平台、路径、运行环境及测试限制。

已有事实、团队决定、待确认建议分别标记。通用三层架构、JWT、REST 或某个前端库不自动成为仓库规范。

## 文档目录与需求设计产物

先记录仓库实际的文档分类和映射。若已有 `docs/architecture/`、`docs/designs/`、`docs/plans/`，优先复用；没有既有约定时才使用 `docs/requirements/<需求编号>/<需求编号>-<repo-id>-<类型>.md`。按 impact/spec/design/tasks/review 职责输出，若项目已有不同归档约定，确认编号和路径映射后采用。

设计必须引用需求/验收编号、固定产品版本和代码基准，区分复用、修改、拟新增；具体设计深度按项目需要补充。`design-guidelines.md` 必须告诉后续专家每类产物的实际目录、命名和权威入口。

## 验证与评审

记录实际构建、类型检查、测试入口和适用平台；设计阶段说明验证计划，不虚构运行结果。明确哪些决定由产品、哪些由研发确认，缺失项怎么处理。

## 工作范围

设计阶段读取代码、按授权写文档；不自动改业务代码、安装依赖、重构、提交、发布或写外部系统。基线初始化不要求补齐全部历史功能规格。
