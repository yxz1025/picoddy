# 需求澄清与多仓库增量设计

## 1. 接收输入与登记仓库

接收需求单编号、PRD 固定版本、对应原型和产品评审结论。复用已有信息，只追问实质缺口。缺少编号时可先在会话中分析，正式归档前确认稳定编号；有产品系统正式编号则沿用，不另起同义编号。

登记每个仓库的稳定 `repo_id`、远程来源、本地位置、系统职责、基准分支/提交、相关本地未提交改动、规范入口及负责人。区别“修改”“依赖”“参考”，仅修改仓库默认生成实现设计。一个需求可关联用户端、管理后台、多个服务，一个仓库也可包含多个模块。

只读取已提供或授权访问的仓库，不凭地址声称已检查代码。克隆、切分支、更新代码及写入需符合授权；不覆盖本地改动。确认牵头仓库，不默认选择后端；尚未指定时先在会话列问题，不随意落库。

## 2. 仓库规范与最小基线

先读取 [项目规范发现与路径解析](repository-context-routing.md)，从仓库规则和 docs 索引发现入口，再查找候选核实范围。产物按已确认目录映射写入，docs/requirements 仅为无约定时默认位置。按仓库或模块分别选择技术参考。

先读取仓库自身的执行规则、已有 docs 分类和规范入口，并按需读取其中要求的上下文、架构、接口、组件和测试资料。不能固定假设规范都位于 `docs/development/`：若仓库已有 `docs/architecture/`、`docs/designs/`、`docs/plans/` 等目录，先依据实际内容建立路径映射。仓库缺少这些入口时，使用随包的 `../../skills/repository-bootstrap/SKILL.md` 初始化；初始化默认生成草案，不能把推断直接当成规范。

缺少规范时读取 [仓库设计要求模板](repository-guidelines-template.md)，提出最小基线草案；在授权位置整理 `project-context.md`、`architecture.md` 或引用已有资料，由研发核实关键约束。未获核实的推断保留标记，不冒充项目规范。

先识别全局结构，再深入需求相关模块，不强制补齐所有历史模块的 spec。现状说明和需求增量分离。项目规范与通用参考冲突时遵循项目规范；需求与规范发生实质矛盾时报告影响并请求负责人决定，不悄悄改变任一方。

## 3. 先审查产品资料，再用代码核实问题

检查业务目标、用户、范围、状态流、字段含义、权限、异常、原型一致性和验收条件。只追问影响本次设计的缺口，不机械填充与需求无关的指标。

读取相关页面/路由、调用链、业务逻辑、数据访问、鉴权、接口/组件、测试。用仓库 ID、提交、相对路径和符号定位证据；行号只能辅助，不能替代代码基准。记录本地未提交改动是否影响分析，必要时用可核验快照标识，不将工作区状态冒充某个提交。

建立“需求条目 → 仓库/模块 → 当前证据 → 差距 → 影响”的映射。已存在对象、拟新增对象和未核实对象明确区分；发现相似文件不等于已经核实完整业务链路。

需求审查和代码分析可迭代。代码是现状证据，不等于业务真理；不能因现有接口只支持一种行为，就替产品决定需求也只能如此。

## 4. 提出问题并等待补充

发现规则缺失、歧义、PRD/原型冲突、不可用依赖、明确安全风险或不合理约束时，先输出问题，不批量生成完整 spec/design/tasks。读取 [产物与归档规范](engineering-artifacts.md) 中的问题记录格式，在牵头仓库保存 `<需求编号>-questions.md`，或在尚无授权位置时先会话输出。

每个问题带稳定 ID、对应需求/验收条目、证据、设计影响、阻塞范围、待确认角色及必要的选项取舍。按依赖和影响优先提出当前需要回答的问题，避免泛泛要求“补全 PRD”或一次倾倒无关问题。

例如：原型有批量审核，PRD 未定义部分失败，现有接口只支持单条。应让产品决定是否允许部分成功，并说明接口、事务、反馈及验收影响，不能直接设计循环调用视为解决。

- 业务规则、范围、验收：产品/业务确认。
- 代码事实、技术约束、仓库职责：研发确认。
- 涉及范围与技术成本取舍：相关人员共同确认。
- 信息不足或代码不可访问：列明具体缺口和受影响范围，不能编造补齐。

对“不合理”的判断需有证据，不因个人偏好否定需求。可给有限方案草图帮助决策，但标为候选，不能当正式方案。

## 5. 问题闭环与设计准入

问题状态：提出 → 待确认 → 已答复待回写 → 已回写待复核 → 已关闭。延期或不采纳保留原因、决定人及风险。

产品回复需反映在 PRD、原型、验收项或明确权威关系的受控补充记录中。架构师可建议改法，但未经授权不直接改产品文件。记录实际回复来源与确认版本，复核消除冲突后再关闭；一句聊天回复不自动使全部产物一致。

只有以下条件满足，才进入对应范围的正式设计：

- 目标、范围、关键业务规则及验收条件明确。
- 产品资料间无阻塞冲突，未决项影响有说明。
- 仓库、规范、关键代码和分析基准可核实。
- 责任分工和关键依赖已确认到可设计程度。
- 本轮输入基线和必要决定已由对应人员确认。

阻塞问题未解决时，停在澄清阶段并清楚请求下一项确认。独立、已确认部分可以在明确范围后继续部分草案，非阻塞问题保留；不得把整体标记可开发。已有答复不重复询问，未获答复不以假设偷偷关闭问题。

## 6. 详细设计与任务拆分

开始输出前读取 [产物与归档规范](engineering-artifacts.md)。统一产品行为与共享契约，各仓库只描述自身责任。

详细方案需包含需求映射、现有实现、复用点、修改/拟新增文件和职责、关键流程、接口字段/类型/空值/校验/错误、权限、跨仓库依赖和验证设计。事务、并发、幂等、性能、迁移等仅在实际需要且仓库规范允许时设计，不为套通用模板增加框架或重构。

前端分别遵循用户端与后台仓库的组件及状态管理规范；后端遵循现有业务层、数据访问和权限约定。原型解释交互，不替代 PRD 业务规则。开发无需重新猜关键规则，但不要求提前写完整生产代码。

每个任务关联需求和验收编号，给出仓库、模块、前置依赖、工作内容、完成标准及验证方法。跨仓库任务编号可引用，不在多处复制维护任务正文。

生成 tasks 前读取 [任务评估与执行流程](task-review-and-execution.md)。任务默认草案/待评估，执行未开始；交人评估粒度、范围、依赖、工作量和验证，按实际意见修订并确认基线。设计评审不能自动替代任务评估，更不能自动授权开发。

共享契约优先引用已有权威来源，新接口原则上由提供方维护；牵头仓库记录分工、版本和依赖顺序。调用方不得另行定义矛盾字段或状态。

## 7. 写入、自检与评审

按 [研发产物自动校验](artifact-validation.md) 执行随包校验器，检查已登记范围的身份、文件引用、验收映射、任务依赖及引用版本。修订后重跑，结果关联本轮清单和文档版本；工具失败或未执行需如实记录。结构化索引与正文的一致性仍须审查，不把脚本通过当作设计就绪。

写入前核对目标仓库、路径、已有文件和用户修改，按归档规范安全增量更新。不同机器使用各自本地映射，文档引用不用个人绝对路径。多仓库部分写入失败要逐项报告，重试先检查已成功部分，不宣称整体原子完成。

核对编号/元信息一致、需求覆盖、代码证据、项目规范、跨仓库契约、文件可定位及问题闭环。静态设计检查不等于构建或系统测试，未执行项写未验证。评审单独记录产品对业务解释的确认、研发对技术方案的意见以及测试对可验证性的意见，不伪造批准人、时间或通过结论。

最后输出每仓库文件位置、产品/代码基线、澄清状态、检查结果、人工评审状态和阻塞项。设计未就绪可交付草案，不称可开发。代码实现需后续明确授权；不预填提交、自测或提测成功结果。

## 8. 修订与失效处理

PRD、原型、仓库基准或契约变化时，先识别影响，再重开相关问题、更新设计和任务，标记旧评审失效范围。保存历史记录，不能自动继承旧版通过结论，也不重编稳定需求编号。
