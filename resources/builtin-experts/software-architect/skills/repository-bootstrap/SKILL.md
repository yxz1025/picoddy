# 仓库规范初始化

将一个代码仓库整理为可被后续需求设计读取的最小文档基线。目标是记录当前项目真实事实、已确认约束和待确认问题，不是重构代码，也不是凭通用最佳实践发明一套架构。

## 核心流程

```text
确认仓库与权限
  ↓
读取项目规则、说明、配置和代码结构
  ↓
识别技术栈、模块、依赖、运行/构建/测试入口
  ↓
分析架构、调用链、数据和权限边界
  ↓
区分事实、已有规范、推断和待确认项
  ↓
生成扫描报告和文档草案
  ↓
人工评估并确认
  ↓
按授权写入仓库现有文档分类或默认目录
```

默认先做只读扫描和草案输出。只有用户明确授权写入目标仓库，才创建或修改文档。用户要求直接初始化并写入时，仍须先检查现有文件、未提交改动和覆盖风险，再执行。

## 扫描范围

优先读取以下内容，存在什么读取什么，不假设文件一定存在：

- `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、`README.md` 及已有 `docs/`。
- `package.json`、`pom.xml`、`go.mod`、`Cargo.toml`、`pyproject.toml` 等依赖和脚本文件。
- Docker、CI/CD、构建、环境示例和部署配置。
- 前端入口、路由、页面、组件、状态和接口客户端。
- 后端入口、路由、控制器、服务、数据访问和任务调度。
- 数据库模型、迁移、种子数据、鉴权和权限实现。
- 测试目录、测试脚本、测试配置和 CI 中的检查命令。

先看全局结构，再深入当前需求相关模块。大型仓库应报告扫描范围和未扫描范围，不声称已经理解全部代码。

## 文档目录识别与输出

入口发现顺序：读取仓库及模块规则 → README.md / docs/README.md 索引 → 查找 design-guidelines.md 或其他实际开发规范 → 核实候选的内容、适用范围和状态。多个候选按范围使用，同范围冲突先核实，不凭名称或更新时间任选。本规则自包含，独立安装本技能无需依赖专家包。

先检查仓库已有文档目录和命名约定。常见分类包括：

```text
docs/architecture/   # 架构、系统边界、模块和技术决策
docs/designs/        # 需求/功能详细设计
docs/plans/          # 实施计划、任务拆解和执行计划
docs/development/    # 研发规范、项目上下文、开发约束
```

目录含义以仓库已有内容和规则为准，不能仅凭目录名称武断判断。若仓库已经有 `docs/architecture/`、`docs/designs/`、`docs/plans/`，优先在这些目录下补齐或更新对应文档，并在 `design-guidelines` 中记录映射。例如：

| 文档职责 | 已有目录优先位置 |
| --- | --- |
| `architecture.md` | `docs/architecture/` |
| 需求级 `design.md` | `docs/designs/` |
| 需求级 `tasks.md` | `docs/plans/` |
| 研发规范和项目上下文 | 已有开发文档位置；没有时才使用 `docs/development/` |

只有仓库没有可识别的文档约定时，才建议使用以下默认布局：

```text
<repository>/docs/development/
├── design-guidelines.md
├── project-context.md
└── architecture.md
```

### `project-context.md`

记录仓库职责、服务边界、技术栈、目录结构、运行/构建/测试入口、外部依赖、支持平台、代码基准和未分析范围。

### `architecture.md`

记录当前模块边界、主要调用链、数据流、权限边界、外部系统、重要现有决策、已知技术债务和代码证据。描述现状，不把目标架构写成当前架构。

### `design-guidelines.md`

记录后续需求设计必须遵循的约束：必读文档、目录和分层、前后端/数据/接口/权限/错误处理约定、文件命名与归档方式、允许修改范围、测试验证要求、评审规则及设计与开发边界。

只有负责人确认的内容才能标为正式项目规范。代码中发现的做法默认标为“代码现状”，不能自动升级为团队约束。

## 信息分类

文档中明确区分：

| 分类 | 含义 |
| --- | --- |
| 代码事实 | 可由文件、符号、配置、命令或提交核验 |
| 已确认规范 | 团队或负责人明确认可的约束 |
| 架构建议 | 专家提出的候选做法，不代表项目决定 |
| 待确认项 | 证据不足、文档冲突或责任人未确认 |
| 历史例外 | 已知存在但不应推广的旧实现 |

每个关键结论记录文件路径、符号/配置项和分析提交；本地未提交改动单独说明。不可读取的代码、失效命令和不确定职责标记为未核实，不能编造。

## 老仓库处理

老仓库没有规范文档时，只建立与后续需求设计有关的最小基线：

1. 复用已有文档并标出过期或冲突内容。
2. 分析实际入口、模块和测试，不补写所有历史功能的规格。
3. 生成草案供负责人确认。
4. 将不确定内容留在待确认项，不用模板默认值填空。

初始化不自动重构、升级依赖、补测试、切换架构、修改业务代码、删除旧文档或覆盖用户未提交修改。

## 写入规则

- 已授权初始化并写入时可直接落盘 draft，规范批准另行记录；写草案不重复请求已有授权。
- 在现有 docs/README.md 或获授权的规则入口增量登记规范的相对链接、范围、状态及产物目录映射；没有索引可在授权 docs 范围内创建，避免复制正文或更改无关规则。
- 入口登记不在授权范围时报告待登记项和准确位置，不宣称自动发现完成。其他专家是否自动读取取决于其规则和加载方式，生成文件本身不保证自动加载。

- 写入前检查目标目录和文件是否已有内容；已有规范优先增量更新并保留历史版本。
- 不使用个人电脑绝对路径作为仓库身份或跨仓库引用。
- 记录 `repo_id`、文档版本、状态、分析提交、负责人和更新时间；没有真实确认信息时使用 `draft` 或 `pending-confirmation`。
- 文档使用 Markdown 和相对路径；引用不存在的文件必须标记为待补充，不能伪造链接。
- 可在 Windows、macOS、Linux 使用的路径和命名约定，不依赖 Unix 权限或 shell 特性。

## 交付后使用

完成初始化后，交付已登记的入口；遵循该入口的需求设计专家按以下顺序读取：

1. 仓库规则文件（`AGENTS.md`、`CLAUDE.md` 等）。
2. 按仓库规则和 docs 索引定位规范，再读取其中的目录映射；无索引时按前述发现规则核实候选。
3. 项目上下文文档。
4. 架构、设计、计划等与当前需求相关的文档。
5. 本次需求相关模块的代码和测试。

若文件不存在、状态为草案或代码基准已变化，先报告并重新核实受影响内容；不能把初始化文档当作永远正确的缓存。仓库规范与通用架构参考冲突时，优先仓库已确认规范；需求与规范冲突时提出问题，由负责人决定。文档目录映射本身也必须记录实际路径，不能让后续专家猜测。

## 完成标准

初始化完成至少要报告：扫描范围、代码基准、已生成/更新文件、事实与推断边界、待确认项、未扫描范围和文档状态。没有负责人确认时，结论是“草案已生成”，不是“规范已生效”。
