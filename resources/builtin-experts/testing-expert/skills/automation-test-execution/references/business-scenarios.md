# 单端与跨端业务场景编排

## 范围和入口

测试单位是业务场景，不是仓库。一个端可关联多个仓库，一个仓库可承载多个端。按用户指定范围和已确认业务链路确定 single-target/cross-target；只有一个端时默认设计该端覆盖，不虚构缺失端。跨端需要各端的稳定 targetId、入口、仓库映射、角色、认证引用和环境。范围不明时只问是否覆盖跨端协作，不因仓库数量自动扩大范围。

先生成用例：读取资产→确定覆盖范围→生成交付→询问执行→补齐各端配置和数据条件→生成脚本→准备数据→执行→清理→反馈。
直接启动：用户明确授权本轮测试→补齐范围、各端入口及数据条件→生成用例与脚本→检查执行前置条件→准备数据→执行→清理→反馈；不再次索要启动确认。
“先不测试/只生成”优先；可以设计 fixtures，但不能执行造数、打开浏览器或开发者工具。缺域名不阻碍纯业务用例设计。授权执行不是授权生产操作、部署、安装或任意数据库写入。

## 场景与端配置

使用 [场景配置示例](../templates/business-scenario.example.json) 的结构，在选定业务仓库中按既有规范生成正式配置。该文件是编排契约示例，不是既有 run-wechat.cjs 的输入。它含明显占位值，不能直接运行。凭据仅用引用，绝不在清单中写 token、密码或 storageState 内容。

每个场景记录 SC-ID、关联 TC-ID/AC-ID、必测标记、前置条件、步骤及依赖、数据输入输出、每一步业务断言、预期最终状态和清理策略。业务 ID 按 producer step/output key 传递，不能取列表第一条；可传订单/租户/用户等必要标识，不通过共享上下文传播会话 token。

每个目标记录 kind、repositoryIds、环境、Web baseUrl/entryPath 或小程序 projectPath/cliPath/appId、角色及 credentialRef。不同端必须确认使用同一测试业务环境及兼容版本，角色/租户/数据权限满足本场景；不得假定不同平台账号自动对应同一个人。小程序含启动场景值时记录真实路由和参数含义，不混淆微信数字 scene 与业务 query.scene。

## 数据准备与清理

区分被测动作和前置条件。若用例验证 A 创建→B 处理，A 创建必须走真实被测入口；用接口造出订单只能验证后半段，报告必须缩小覆盖范围。
基础账号、商品、库存等前置数据优先用现有测试业务 API/fixture。无可用接口时使用已授权页面流程，或列出人工准备项：数据 ID、环境、所属账号/租户、状态、有效期及完成确认。未经明确授权不直接写数据库；获授权也必须说明关联表、事件、副作用与清理约束。
每轮唯一 runId，按场景分配隔离标识，记录 created/reused/manual 数据及来源。仅清理本轮创建且确认归属的数据，不能删除共享或人工数据。创建返回真实 ID 后立即写受控本地账本；setup 部分失败也进入清理。支付/订单采用已授权取消或补偿业务接口，不能随意删库记录。
异步到达使用指定业务 ID 的有限条件轮询，记录截止时间；不能固定睡眠后直接判成功。创建/审核等非幂等请求超时后先只读核对，不盲重试，结果未知时阻塞并保留数据。
数据未准备完成标 blocked；依赖步骤标 not_run，不能算业务缺陷或通过。结束和失败都执行 try/finally 清理，取消停止新步骤并尝试有界清理；强制终止无法保证 finally 时报告 cleanup_unknown 和待清理清单。

## 统一执行入口

专家结合真实仓库生成一个场景入口（如 tests/automation/run-business-scenarios.cjs），复用项目测试框架及实际 SDK；不把示例当作已实现的运行器。不新增 MCP 依赖。现有 run-wechat.cjs 保持单端独立运行，不可并发启动多个实例争用同一开发者工具项目。

Web/H5/微应用采用 Playwright 独立 browser context 隔离各角色登录态。小程序用官方 miniprogram-automator 的 launch/connect 和页面 API，并按连接所有权清理；同一开发者工具项目串行使用，需要不同微信身份时明确人工切换/独立环境条件，不能假定浏览器隔离机制适用小程序。

统一入口执行以下职责：
1. 校验所有目标/脚本、步骤 ID 唯一性、依赖存在且无环、数据引用 producer 必为已完成依赖；检测未替换占位符和缺失真实断言。
2. 生成不可覆盖的运行目录，记录资产版本、各仓库 commit/dirty/脚本 hash、目标入口、预期业务版本及未核验项；凭据不进入报告。
3. 执行 setup 并立即持久化数据账本；初始化目标适配器，生命周期由入口管理。
4. 按依赖顺序执行步骤，传递真实结果，使用有界超时和可取消操作。超时不能仅 Promise.race 后继续复用仍在执行的上下文；停止或隔离当前操作，再决定后续。
5. 记录逐步骤 TC/AC、目标、角色、业务 ID、断言和截图/trace。前序失败只阻塞依赖步骤；独立场景可继续，但默认顺序执行。
6. finally 执行本轮清理并关闭自己启动的上下文/开发者工具，再原子写状态和报告。进程退出、工具启动、单步成功都不能代替业务断言。

A 创建→B 展示/审核→A 核验的步骤必须共用同一业务 ID。只有无依赖、账号/数据/环境资源均隔离的场景可并行；冲突共享资源必须串行或加已有资源锁。多端结果必须属于同一 runId 的明确链路，不能拼接历史或各端独立通过记录。

## 按需子 Agent

单端或简单链路由主专家直接完成。复杂多端且宿主支持时，可按端/仓库委派独立的只读分析或脚本生成任务；任务约定范围、资产版本、targetId、输入输出、脚本路径和交付标准。不同子 Agent 不同时修改同一文件，也不各自执行造数或业务流程。
主专家合并 TC-ID/AC-ID、接口契约和数据流，审阅断言后启动统一执行入口。委派本身不扩大权限；缺子 Agent 能力时顺序完成，不能把它作为运行前置条件。只有用户明确要求并行执行且满足资源隔离时才委派执行，依赖链仍由主入口管理。

## 结果反馈

按 SC-ID 汇总 passed/failed/blocked/not_run/interrupted/incomplete/flaky，附各端步骤、已覆盖 TC/AC、业务 ID、真实证据与清理结果。业务断言失败和配置/登录/造数失败分别归类。场景全部必测步骤真实通过且清理符合策略才可通过；零执行、必测缺口、未知结果、清理失败不得全绿。重试成功标 flaky，并保留第一次证据。
单端只评价该端覆盖；模拟器不能代表真机；未核验部署版本必须声明。反馈实际问题和下一步所需信息，未经授权不改业务代码、部署或提交远端缺陷。报告脱敏，敏感原件受控保存。
